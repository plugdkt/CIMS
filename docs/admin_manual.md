# คู่มือผู้ดูแลระบบ CMIS (สำหรับบทบาท ADMIN และ AUDITOR)

เอกสารนี้สำหรับผู้ดูแลระบบ (ADMIN) และ AUDITOR (ปัจจุบันคือผู้ดูแลคลังสิทธิ์เท่า LAB_MANAGER — ดูหัวข้อ 8) — ครอบคลุมงานที่ไม่มีในคู่มือผู้ใช้ทั่วไป
(`docs/user_manual.md`) เช่น การกำหนดสิทธิ์ผู้ใช้, การจัดการห้องปฏิบัติการ, การตรวจสอบความสมบูรณ์ของ
บัญชีคุม, และงานที่เกี่ยวข้องกับ PDPA

> **ข้อควรทราบสำคัญ**: บทบาท ADMIN **ไม่มีสิทธิ์เขียนบัญชีคุมวัสดุ (ledger) โดยตรง** (ไม่มี `ledger.*` ฝั่งเขียน)
> ดังนั้น **ปรับปรุงยอด (`ledger.adjust`), อนุมัติผลตรวจนับ, อนุมัติการทำลาย/ตัดจำหน่าย
> (`disposal.approve`), นำเข้า/ยืนยันใบรับ IMS (`ims.manage`), อนุมัติใบเบิก (`requisition.approve_scientist`) และจ่าย/คืนของตามใบเบิกไม่ได้** — เป็นการออกแบบตั้งใจตาม spec §3
> (Separation of Duties) **แต่ไม่ได้แปลว่า ADMIN ไม่มีผลต่อบัญชีคุมเลย**: เมื่อ ADMIN ยืนยันใบรับของ (GRN)
> ระบบจะสร้างแถว "รับเข้า" (RECEIVE) ในบัญชีคุมให้ **ทางอ้อม** โดยบันทึกผู้ทำรายการเป็น ADMIN (CEO ตัดสิน E7 2026-10-30)
> ADMIN **ทำได้**: รับของเข้าคลัง (`receiving.manage`), เปิดรอบ/ดำเนินการตรวจนับสต๊อก
> (`stocktake.manage`), ขอทำลาย/ตัดจำหน่าย (`disposal.request`) และตรวจสอบ Hash Chain / ดูคลัง IMS / ดูรายงานแบบอ่านอย่างเดียว
> (CEO ยืนยัน 2026-10-30 ว่าเป็นไปตามระบบ) ส่วนงานที่ ADMIN ไม่มีสิทธิ์ ต้องให้บัญชีที่มีบทบาท LAB_MANAGER/AUDITOR ดำเนินการแทน

## 1. การกำหนดสิทธิ์ผู้ใช้งาน (Role Provisioning)

ระบบยืนยันตัวตนกลาง (MEDSCI ACC) รู้แค่ "ผู้ใช้นี้คือใคร" — **ไม่รู้จักบทบาทของ CMIS เลย** ผู้ใช้ทุกคนที่
ล็อกอินครั้งแรกจะไม่มีสิทธิ์ใด ๆ จนกว่า ADMIN จะกำหนดให้ (deny-by-default)

1. เมนู "ผู้ใช้งานและสิทธิ์" (`/admin/users`)
2. ค้นหาผู้ใช้ด้วยชื่อหรือ username
3. เลือกบทบาทที่ต้องการมอบให้ (เลือกได้มากกว่า 1 บทบาทต่อคน ถ้าจำเป็น เช่น คนที่เป็นทั้ง SCIENTIST และ
   ADVISOR)

**ตารางบทบาทและสิทธิ์โดยสรุป**:

| บทบาท | สิทธิ์หลัก |
|---|---|
| `STUDENT` | สร้างใบขอเบิก, ดูใบขอเบิกของตนเอง, ดูทะเบียนสารเคมี |
| `STAFF` | เหมือน STUDENT (แต่ไม่มีขั้นตอนอาจารย์ที่ปรึกษา) |
| `ADVISOR` | รับอีเมล (ลิงก์ 72 ชั่วโมง) ใบขอเบิกของนิสิตในความดูแล และกดอนุมัติ/ไม่อนุมัติ — **ใบเบิกของนิสิต: อาจารย์อนุมัติแล้วสถานะเป็น "อนุมัติแล้ว" ทันที ไปจ่ายของได้เลย ไม่ต้องผ่านขั้นนักวิทยาศาสตร์/ผู้ดูแลคลังอีก** (CEO ตัดสิน 2026-11-04 แบบ ก.) ยังเป็นประตูกั้นจริงตาม BR-02: นักวิทยาศาสตร์/ผู้ดูแลคลังพิจารณาใบเบิกนิสิตที่อาจารย์ยังไม่อนุมัติไม่ได้ (ไม่อนุมัติ = ใบเบิกจบ); ใบเบิกนิสิตเก่าที่ค้างสถานะ "อาจารย์อนุมัติแล้ว" ยังให้นักวิทยาศาสตร์/ผู้ดูแลคลังตัดสินต่อได้; ผู้เบิกที่ไม่ใช่นิสิตข้ามขั้นอาจารย์ (CEO คืนกฎ 2026-10-30) |
| `SCIENTIST` | **พิจารณา (อนุมัติ/ไม่อนุมัติ) ใบขอเบิกของบุคลากรในสาขาตนได้ทุกชนิด และจ่ายของตามใบที่อนุมัติแล้ว** (CEO กลับกติกา 2026-11-04 — นักวิทยาศาสตร์ทุกคนในสาขาเวียนเป็นเวรกัน ระบบไม่ระบุตัวบุคคล) สร้าง/ดูใบขอเบิกของตนเอง, ดูบัญชีคุม/ทะเบียนวัสดุ, เปิดดูของในคลังกลางสาขา (ไม่เห็นราคา), อนุมัติคำขอยืมและเป็นผู้อนุมัติแทนการปรับยอด/ปลดระวางของให้ยืมของสาขาตน — **ข้ามสาขาไม่ได้ และบัญชีที่ไม่มี `lab_id` ทำสิ่งเหล่านี้ไม่ได้เลย**; **ไม่มี**สิทธิ์รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลาย/ตัดจำหน่าย, ดูรายงาน (ย้ายไปผู้ดูแลคลังเมื่อ 2026-09-21/22) |
| `LAB_MANAGER` | ผู้ดูแลคลังประจำสาขา: พิจารณาใบขอเบิก **และจ่ายของตามใบเบิกได้ (ตั้งแต่ 2026-11-04) เฉพาะสาขาและชนิดที่รับผิดชอบ**, อนุมัติจ่ายเกิน 10%, รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลายและอนุมัติทำลาย/ตัดจำหน่าย, อนุมัติปรับปรุงยอด, ดูบัญชีคุมวัสดุ (`ledger.view`), จัดการทะเบียนสารเคมี/ผังจัดเก็บ/สมาชิกที่เบิกได้ในสาขา, จัดการคลัง IMS (นำเข้า/ยืนยัน), ดูรายงาน |
| `ADMIN` | จัดการผู้ใช้/สิทธิ์/ห้องปฏิบัติการ/หน่วยนับ, ตรวจสอบ Hash Chain, เข้าถึง Audit Log, รับของเข้าคลัง, เปิดรอบ/ดำเนินการตรวจนับสต๊อก, ขอทำลาย/ตัดจำหน่าย, ดูใบขอเบิกทั้งหมด/ทะเบียนวัสดุ/รายงาน/คลัง IMS/หน้ารายการปรับปรุงยอด (ดูอย่างเดียว) (**ไม่อนุมัติใบเบิก ไม่จ่าย/คืนของ ไม่อนุมัติคำขอยืม และไม่เป็นผู้อนุมัติแทนการปรับยอด/ปลดระวางของให้ยืม** — CEO ยืนยัน 2026-11-04; ไม่อนุมัติปรับยอด/ผลตรวจนับ/การทำลาย และไม่นำเข้า/ยืนยัน IMS) |
| `AUDITOR` | **ไม่ใช่บทบาทอ่านอย่างเดียวอีกต่อไป** (ปรับบทบาทเมื่อ 2026-09-21) — เป็นผู้ดูแลคลังประจำสาขาอีกรูปแบบหนึ่ง สิทธิ์เท่า LAB_MANAGER ทุกประการ (ทั้ง LAB_MANAGER และ AUDITOR ไม่มี Audit Log/ตรวจ Hash Chain — เป็นของ ADMIN เท่านั้น) |

**หมายเหตุ**: ระบบยังบังคับที่ระดับ transaction จริง (ไม่ใช่แค่ที่หน้าจอ) ว่า **ผู้อนุมัติปรับปรุงยอด ต้องไม่ใช่
คนเดียวกับผู้สร้างรายการ** และ **ผู้อนุมัติผลตรวจนับ ต้องไม่ใช่ผู้นับรายการที่มีผลต่างนั้น** ส่วน
**การทำลาย/ตัดจำหน่ายไม่มีการแยกผู้ขอ/ผู้อนุมัติ** — ผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) คนเดียวขอและอนุมัติเองได้
(CEO ตัดสินใจแล้ว 2026-09-22 "คนเดียวทำได้จบ" อย่าเข้าใจว่าเป็นช่องโหว่)

### ผู้อนุมัติใบเบิก และการอนุมัติ/จ่ายของตัวเอง (approvals.md K, 2026-11-04) [ร่าง รอ CEO ตรวจ]

- **ใครอนุมัติใบเบิกบุคลากร:** นักวิทยาศาสตร์ **ทุกคน** ในสาขาของใบเบิก (ทุกชนิด รวมสารควบคุม) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR)
  เฉพาะสาขา+ชนิดที่รับผิดชอบ **ADMIN อนุมัติใบเบิกไม่ได้** ทุกบทบาทต้องมี `lab_id` ตรงกับสาขาของใบเบิก (**บัญชีที่ไม่มี `lab_id` อนุมัติ/จ่ายไม่ได้เลย**
  ระบบไม่ถือว่า "ว่าง = ตรงกัน") บัญชี ADMIN ที่ถือบทบาทผู้ดูแลคลังด้วย (Super Admin) จึงถูกจำกัดตามสาขาของตนเมื่อใช้สิทธิ์ผู้ดูแลคลังนี้ — **เปลี่ยนจากเดิมที่ข้ามสาขาได้**
- **ใครจ่ายของ:** นักวิทยาศาสตร์ (สาขาตน ทุกชนิด) และผู้ดูแลคลัง (สาขาตน เฉพาะชนิดที่ถือ; ใบผสมสองชนิดต้องถือทั้งสอง) ADMIN จ่ายไม่ได้
- **ใบเบิกนิสิต:** อาจารย์ที่ปรึกษาอนุมัติแล้ว → "อนุมัติแล้ว" ทันที พร้อมจ่าย (ข้ามขั้นนักวิทยาศาสตร์/ผู้ดูแลคลัง) ระบบแจ้งเตือน "พร้อมจ่ายของ" ไปยังผู้จ่ายของสาขา
- **อนุมัติพร้อมกัน:** ถ้านักวิทยาศาสตร์สองคนกดพร้อมกัน ระบบล็อกแถวและตรวจสถานะซ้ำ คนที่กดก่อนชนะ อีกคนได้ข้อความปฏิเสธ (ไม่มีแถวอนุมัติซ้ำ)
- **อนุมัติ/ไม่อนุมัติ/จ่ายของใบเบิกของตัวเอง "ทำได้" (CEO ตัดสิน ไม่มีกฎห้าม)** แต่ระบบบันทึก Audit Log เป็นการควบคุม:
  - ทุกการตัดสินของนักวิทยาศาสตร์/ผู้ดูแลคลังบันทึก `REQ_APPROVE` หรือ `REQ_REJECT`; ถ้าผู้ขอ = ผู้อนุมัติ บันทึกเป็น **`REQ_SELF_APPROVE` / `REQ_SELF_REJECT`**
    (ฟิลด์ `self_approval = true` ในค่าใหม่ของ log)
  - การจ่ายของที่ผู้จ่ายเป็นผู้ขอ หรือผู้อนุมัติ หรือผู้อนุมัติจ่ายเกิน 10% บันทึก **`REQ_SELF_ISSUE`** (ระบุว่าเป็นกรณีใดใน `issuer_is_requester` / `issuer_is_approver` / `issuer_is_overage_approver`)
  - **รายงาน "ใบเบิกที่ผู้ขอเป็นผู้อนุมัติ/ผู้จ่ายเอง"** (หน้ารายงาน แท็บ `self_approval` กรองตามสาขาและวันที่สร้างใบเบิก; ผู้ดูแลคลังเห็นสาขาตน, ADMIN เห็นทุกสาขา) —
    เป็นหน้าจอเท่านั้น ไม่มีส่งออกไฟล์ **ต้องมีคนเปิดดูเป็นประจำ** ไม่เช่นนั้นการควบคุมนี้ไม่มีผล
  - ใบเบิกที่ ผู้ขอ = ผู้อนุมัติ = ผู้จ่าย และจ่ายเกิน 10% ได้ครบวงจรโดยคนเดียว (ผู้ดูแลคลังถือ `requisition.issue_override`) — CEO รับทราบว่าควบคุมด้วยธง/รายงานอย่างเดียว
- **แจ้งเตือน:** ใบที่รออนุมัติ → แจ้ง "ในระบบ" นักวิทยาศาสตร์ที่ active ทุกคนของสาขา + ผู้ดูแลคลังที่ถือชนิดนั้น; **อีเมลส่งเฉพาะผู้ดูแลคลัง** (ไม่ท่วมกล่องนักวิทยาศาสตร์ เพราะเวียนเวร
  ระบบไม่รู้ว่าใครอยู่เวร) ถ้าไม่มีใครในสาขาอนุมัติได้เลย ระบบแจ้ง ADMIN (`requisition.no_approver`) ให้ไปจัดคนในสาขา เพราะ ADMIN อนุมัติเองไม่ได้
- **ข้อยกเว้นของ "ADMIN อนุมัติไม่ได้":** จริงเฉพาะบัญชีที่ถือบทบาท ADMIN ล้วน ๆ ผู้ใช้ที่ถือ ADMIN ร่วมกับ SCIENTIST หรือผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) อนุมัติ/จ่ายได้ตามสิทธิ์ของบทบาทหลังนั้น **ในสาขาของตนเท่านั้น** (ต้องมี `lab_id`)
- **นักวิทยาศาสตร์เห็นใบเบิกทุกใบของสาขาตนที่ไม่ใช่ "ร่าง"** (ทุกสถานะ ทุกชนิด รวมใบที่ตัดสินแล้ว) เพื่อให้เปิดดูคิวอนุมัติและผลการตัดสินได้ ส่วนผู้ดูแลคลังเห็นเฉพาะชนิดที่ถือ; ใบ "ร่าง" ของผู้อื่นไม่เห็น
- **ตรวจจำนวนใบเบิกนิสิตเก่าที่ค้างสถานะ "อาจารย์อนุมัติแล้ว" ก่อน/หลัง deploy (อ่านอย่างเดียว):** ใบเหล่านี้ยังต้องให้นักวิทยาศาสตร์/ผู้ดูแลคลังตัดสินต่อ ใบนิสิตใหม่จะไม่เข้าสถานะนี้อีก
  ```sql
  SELECT l.code AS lab_code, COUNT(*) AS pending_advisor_approved
  FROM requisitions r JOIN labs l ON l.id = r.lab_id
  WHERE r.status = 'ADVISOR_APPROVED' AND r.requester_status = 'STUDENT'
  GROUP BY l.code ORDER BY l.code;
  ```
  หรือ `php artisan tinker --execute="echo AppModelsRequisition::where('status','ADVISOR_APPROVED')->where('requester_status','STUDENT')->count();"` (ผู้ดูแลที่มีสิทธิ์เป็นผู้รัน) ถ้า > 0 ให้แจ้งผู้ดูแลคลัง/นักวิทยาศาสตร์ของสาขานั้นตัดสินให้เสร็จ
- **ตรวจก่อนใช้งานจริง:** ทุกนักวิทยาศาสตร์และผู้ดูแลคลังมี `lab_id`; ทุกสาขามีนักวิทยาศาสตร์หรือผู้ดูแลคลังที่ active อย่างน้อย 1 คนที่รับผิดชอบแต่ละชนิด
  (หลัง seed สิทธิ์ใหม่ด้วย `php artisan db:seed --class=PermissionSeeder` — รันซ้ำปลอดภัย และ **ไม่ถอน** สิทธิ์อนุมัติ/จ่ายของจากบทบาทเหล่านี้อีกแล้ว)

**หน้า "กรอกข้อมูลเพิ่มเติม"** (CEO อนุมัติ 2026-11-02): บัญชีที่มีบทบาท ADMIN ไม่ต้องกรอกเบอร์โทรและรหัสบุคคล
(เว้นว่างได้ ถ้ากรอกเบอร์ ระบบยังตรวจรูปแบบ) ส่วนช่องอื่นยังต้องกรอกตามเดิม บทบาทอื่นทุกบทบาท (นิสิต/เจ้าหน้าที่/
อาจารย์/ผู้ดูแลคลัง) ยังบังคับกรอกเบอร์และรหัสเหมือนเดิม ระบบตัดสินจากบทบาทที่ ADMIN กำหนดให้ ไม่ใช่ค่าที่ผู้ใช้กรอก

## 2. การจัดการห้องปฏิบัติการ (Labs)

เมนู "ห้องปฏิบัติการ" (`/admin/labs`) — เพิ่ม/แก้ไขรหัสและชื่อห้องปฏิบัติการ จำเป็นก่อนที่จะมีใครสร้างใบ
รับของ (GRN) หรือกำหนดผังจัดเก็บได้ (ทุกใบรับของต้องผูกกับห้องปฏิบัติการหนึ่งห้องเสมอ)

### ใบรับของ (GRN) จำกัดตามสาขา (CEO ตัดสิน 2026-10-30)

- **LAB_MANAGER และ AUDITOR** เห็น/สร้าง/แก้ไข/ยืนยัน/ยกเลิกใบรับของได้ **เฉพาะสาขาวิชา (lab) ของตนเอง**
  (สาขาของผู้ใช้คือ `users.lab_id`) — รายการแสดงเฉพาะใบของสาขาตน, ฟอร์มสร้างให้เลือกได้แค่สาขาตน
  ถ้าส่งสาขาอื่นจะถูกปฏิเสธพร้อมข้อความ "สามารถบันทึกใบรับของได้เฉพาะสาขาวิชาของตนเองเท่านั้น"
- **ADMIN** ทำได้ **ทุกสาขา** (ตามการตัดสิน E7)
- ผู้ใช้ที่ไม่ใช่ ADMIN และ **ไม่มี `lab_id`** จะเห็นข้อความ "บัญชีนี้ยังไม่ได้ผูกสาขาวิชา โปรดติดต่อผู้ดูแลระบบ"
  และไม่เห็นปุ่ม "สร้างใบรับของ"
- **ข้อควรทำก่อน deploy**: ตรวจว่า **ผู้ใช้ LAB_MANAGER/AUDITOR ทุกคนมี `lab_id`** (ผูกสาขาแล้ว) มิฉะนั้น
  จะเปิดใบรับของไม่ได้หลังอัปเดตนี้ (อ้างอิง commit 740318b)

### ผู้ดูแลคลังรายชนิด (ITM-2610-052 เฟส 3) [ร่าง รอ CEO ตรวจ]

ใบเบิกแต่ละใบมีชนิดเดียว (สารเคมี หรือ วัสดุสิ้นเปลือง) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) ทำงานกับใบเบิกได้
เฉพาะ **สาขาของตน และชนิดที่ ADMIN กำหนดให้รับผิดชอบ**

- **กำหนดชนิด:** ADMIN เท่านั้น ที่หน้า "ผู้ใช้งานและสิทธิ์" ใต้ชื่อผู้ดูแลแต่ละคนมีปุ่ม "สารเคมี" / "วัสดุสิ้นเปลือง"
  กดเพื่อเปิด/ปิด (ทุกครั้งที่เปลี่ยนบันทึก Audit Log `ITEM_TYPE_CHANGE` ค่าเดิม→ใหม่) บัญชีที่ไม่ถือ
  LAB_MANAGER/AUDITOR กำหนดชนิดไม่ได้
- **ค่าเริ่มต้นคือ "ไม่มีสิทธิ์" (deny by default):** ผู้ดูแลที่ไม่มีชนิดเลยจะ **เปิดดูใบเบิกไม่ได้ (403) อนุมัติไม่ได้
  และไม่เห็นใบในหน้าจัดการใบเบิก** จะเห็นข้อความเตือนให้ติดต่อ ADMIN ผู้ดูแลที่เพิ่งได้บทบาทใหม่ต้องให้ ADMIN กำหนดชนิดก่อนใช้งาน
- **ผู้ดูแลชนิดอื่นเห็นใบเป็น 403:** ผู้ดูแลที่ถือเฉพาะวัสดุเปิดดู/พิมพ์ PDF ใบเบิกสารเคมีของสาขาเดียวกันไม่ได้ (และกลับกัน)
  ใบเดิมที่ผสมสองชนิด: ผู้ดูแลที่ถือชนิดใดชนิดหนึ่ง **ดูได้แต่อนุมัติไม่ได้** ต้องถือทั้งสองชนิดจึงอนุมัติได้
- **การอนุมัติจ่ายเกิน 10% (BR-04):** ผู้อนุมัติต้องถือทุกชนิดของใบนั้น
- **การแจ้งเตือน (แก้ 2026-11-04):** ใบที่รออนุมัติแจ้งผู้ดูแลที่ active ของสาขาเดียวกันที่ถือชนิดนั้น (ในระบบ+อีเมล) **และนักวิทยาศาสตร์ทุกคนของสาขา (ในระบบอย่างเดียว)**
  ถ้าไม่มีใครรับผิดชอบ ระบบแจ้ง ADMIN ทุกคน (`requisition.no_approver`) ให้ไปกำหนดชนิดให้ผู้ดูแล/จัดคนในสาขา **ADMIN อนุมัติใบเบิกเองไม่ได้**
- **ชนิดที่ผู้ดูแลถือใช้กับการจ่ายของด้วย (2026-11-04):** ผู้ดูแลจ่ายของได้เฉพาะใบที่ทุกชนิดอยู่ในชนิดที่ตนถือ (ส่วนนักวิทยาศาสตร์ไม่ถูกจำกัดตามชนิด)
- **ข้อจำกัดที่ CEO รับทราบ:** รายงาน/บัญชีคุม/ตรวจนับ/จำหน่าย/ปรับยอด/IMS ยังจำกัดตามสาขาเท่านั้น ไม่แยกชนิด

**ลำดับ deploy เฟส 3 (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน หลัง CEO อนุมัติ ทำตามลำดับเท่านั้น)**

1. สำรองฐานข้อมูล

   หลังเทสต์ครั้งแรกสร้างตาราง
4. `php artisan managers:backfill-item-types` (ให้ผู้ดูแล LAB_MANAGER/AUDITOR ที่ยังไม่มีแถวชนิดเลย ได้ทั้งสองชนิด)
   - **ใช้ตอน deploy ครั้งเดียว ห้ามรันซ้ำเป็นประจำ:** คำสั่งไม่เพิ่มคืนให้ผู้ที่ถูกตัดเพียงบางชนิด แต่ถ้า ADMIN ตัด

### โมดูลยืม-คืนวัสดุ ขั้น 2: ขอยืม / อนุมัติ / ยกเลิก (ITM-2610-051) [ร่าง รอ CEO ตรวจ]

ขั้น 2 เพิ่ม **เอกสารยืม** ตั้งแต่ผู้ยืมสร้างคำขอจนถึงสถานะ "อนุมัติแล้ว" หรือ "ไม่อนุมัติ/ยกเลิก" **ยังไม่มีการส่งมอบของ รับคืน ต่อกำหนด และเรื่องเสียหาย/สูญหาย**
(ขั้น 3-4) การอนุมัติ **ยังไม่จองของและยังไม่ตัดจำนวนในทะเบียน** ระบบตรวจจำนวนพร้อมให้ยืมสามจุด คือ ตอนส่งคำขอ ตอนอนุมัติ และ (ขั้น 3) ตอนส่งมอบ

**1) สาขา (`users.lab_id`) ต้องมีก่อนจึงยืมได้ และ ADMIN เป็นผู้ตั้ง**
- สาขาของเอกสาร = สาขาของ **ผู้ยืม** (ไม่ใช่ของคนที่กดทำแทน) และรายการของทุกบรรทัดต้องเป็นของสาขานั้น ข้ามสาขาไม่ได้แม้ ADMIN ทำแทน
- ผู้ใช้ที่ไม่มี `lab_id` (รวม ADMIN ที่ไม่มีสาขา) จะถูกพาไปหน้า **"ยังยืมของไม่ได้: รอกำหนดสาขา"** และอีกฝั่งหนึ่ง ผู้ที่ไม่มีสาขาจะไม่เห็นคิวอนุมัติ/รายการของสาขา
- **ตั้งหรือเปลี่ยนสาขา:** หน้าจัดการผู้ใช้และสิทธิ์ (เมนู "ผู้ใช้และสิทธิ์") ช่องสาขาของแต่ละคน บันทึกใน Audit Log ว่า `LAB_ASSIGN` (ค่าเดิม → ค่าใหม่) นี่เป็น **ทางเดียว** ที่เปลี่ยนสาขาที่ตั้งแล้วได้
- **ล็อกสาขา (`User::labLocked()`):** ผู้ใช้ที่มีสาขาแล้วเปลี่ยนสาขาเองจากหน้า "ข้อมูลส่วนตัว" (complete-profile) **ไม่ได้อีก** (ทุกบทบาทรวม ADMIN; ช่องแสดงแบบอ่านอย่างเดียวพร้อมคำอธิบาย; ค่าที่ส่งมาไม่ตรงกับที่เก็บไว้ถูกปฏิเสธ)
  ผู้ที่ยังไม่มีสาขาเลือกได้ **ครั้งเดียว** (บันทึกใน Audit Log เป็น `PROFILE_APPROVAL_FIELDS_CHANGE` ค่าเดิมว่าง → ค่าใหม่) เหตุผล: สาขาเป็นตัวกำหนดว่าใครอนุมัติและยืมของอะไรได้
  ถ้าคนเลือกสาขาผิด ให้แจ้ง ADMIN แก้ตามข้างบน (เป็นการเปลี่ยนที่ควรมีหลักฐานขอเปลี่ยน เพราะกระทบผู้อนุมัติ)

**2) ใครอนุมัติ (approvals.md K, CEO 2026-11-04) [ร่าง]**
- **ขั้นผู้อนุมัติของสาขา (MANAGER):** ผู้ใช้ที่ใช้งานอยู่ ถือ `loan.approve` และมี `lab_id` **ตรงกับสาขาของเอกสาร** = นักวิทยาศาสตร์ (SCIENTIST) ทุกคนของสาขา (เวียนเวร ระบบไม่ระบุตัวบุคคล) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) ของสาขา
  ต้องมีสาขาทุกบทบาท (สาขาว่าง = อนุมัติไม่ได้ ไม่มีกรณี "ว่างเท่ากับว่าง") ข้ามสาขาไม่ได้
- **ADMIN อนุมัติไม่ได้** (ไม่ถือ `loan.approve`) ADMIN ดูเอกสารได้ทุกสาขา แต่ถ้าบัญชีเดียวกันถือ SCIENTIST/ผู้ดูแลคลังด้วยก็อนุมัติได้ **เฉพาะสาขาตนเอง** เหมือนคนอื่น
  ผู้ยืมที่เป็น ADMIN ต้องให้นักวิทยาศาสตร์/ผู้ดูแลคลังของสาขาอนุมัติ ดังนั้นแต่ละสาขาต้องมีผู้อนุมัติที่ active อย่างน้อย 1 คน (ถ้าไม่มี คำขอจะค้าง และระบบแจ้ง ADMIN ทุกคนว่า "มีคำขอยืมแต่สาขาไม่มีผู้อนุมัติ" ให้ตั้งสาขาให้ผู้เกี่ยวข้อง)
- **อนุมัติของตัวเองได้ แต่ต้องมีหลักฐาน:** ถ้าผู้ยืม = ผู้อนุมัติ ระบบอนุญาต และบันทึก Audit Log เป็น `LOAN_SELF_APPROVE` / `LOAN_SELF_REJECT` (ในรายละเอียดมี `self_approval = true`) ผู้ตรวจสอบค้นหาการกระทำสองชนิดนี้ย้อนหลังได้
  (การอนุมัติปกติคือ `LOAN_APPROVE` / `LOAN_REJECT`)
- **ผู้ที่ทำเอกสารแทนผู้ยืม (ผู้ถือ `loan.handout` ที่กรอกให้ที่เคาน์เตอร์) อนุมัติเอกสารนั้นเองไม่ได้** แต่ผู้อนุมัติคนอื่นของสาขาอนุมัติได้
- **ผู้ยืมที่เป็นนิสิต:** ต้องผ่าน **อาจารย์ที่ปรึกษาก่อน** อาจารย์ต้องเป็นคนที่ระบุในเอกสาร (ดึงจากโปรไฟล์นิสิตตอนส่งคำขอแล้วล็อกไว้) ยังใช้งานอยู่ ถือ `loan.approve_advisor` และไม่ใช่ตัวผู้ยืมเอง **ADMIN แทนอาจารย์ไม่ได้**
  ผู้ยืมที่ไม่มีค่าประเภทบุคคล (`person_type` ว่าง) ระบบถือเป็นนิสิต และถ้ายังไม่มีอาจารย์ในโปรไฟล์จะถูกส่งไปกรอกโปรไฟล์ก่อน
  - **[ยังรอ CEO ตัดสิน]** หลังอาจารย์อนุมัติแล้ว ต้องมีผู้อนุมัติของสาขาอนุมัติอีกชั้นหรือไม่ ค่าที่ใช้อยู่ตอนนี้ **มีอีกชั้น** (ตาม BR-L03) ถ้า CEO ตอบว่าไม่ต้อง (เหมือนใบเบิกของนิสิต)
    ให้ผู้พัฒนาเปลี่ยนค่า `student_needs_manager_step` เป็น `false` ใน `config/loans.php` ค่าเดียว (และปรับเทสต์ที่ตรึงค่านี้ไว้ใน `LoanStateTest`) แล้ว deploy ใหม่
  - ไม่บังคับว่า "ผู้อนุมัติขั้นผู้ดูแลสาขา ≠ อาจารย์ที่ทำขั้นแรก" (CEO ยกเลิกค่าเริ่มต้นนี้แล้ว): ถ้าอาจารย์ท่านเดียวกันถือสิทธิ์นักวิทยาศาสตร์ของสาขาและอนุมัติทั้งสองขั้น ระบบทำให้ และบันทึก `advisor_also_approver = true` ใน Audit Log ของขั้นหลัง
- **ลิงก์อนุมัติทางอีเมลของอาจารย์ (signed link):** ใช้ได้ **72 ชั่วโมง** ใช้ตัดสินได้ **ครั้งเดียว** (กดซ้ำไม่มีผล) จำกัด **10 ครั้งต่อนาที** (เส้นทางสาธารณะ ไม่ต้องล็อกอิน) ลิงก์ปลอม/แก้ไข/หมดอายุได้ 403
  อีเมลมีเฉพาะเลขเอกสาร รายการของ จำนวน และวันคืน **ไม่มีชื่อ เบอร์โทร หรือรหัสนิสิต** อาจารย์อนุมัติในระบบหลังล็อกอินได้เช่นกัน (หน้า "รอการอนุมัติ")
  ถ้าอาจารย์ไม่มีอีเมลหรือบัญชีถูกปิด ผู้ยืมต้องให้ ADMIN แก้โปรไฟล์/มอบอาจารย์ใหม่ก่อน (อาจารย์ของเอกสารที่ส่งแล้วเปลี่ยนไม่ได้ ให้ยกเลิกแล้วสร้างใหม่)
- **จำนวนที่อนุมัติ:** ใส่น้อยกว่าที่ขอได้ (ต้องระบุเหตุผล) มากกว่าที่ขอไม่ได้ มากกว่าจำนวนพร้อมให้ยืม ณ ตอนนั้นไม่ได้ ปฏิเสธต้องระบุเหตุผล อนุมัติไม่ได้ถ้าวันคืนผ่านไปแล้ว
  ถ้ามีผู้อนุมัติสองคนกดพร้อมกัน **คนแรกชนะ** อีกคนได้ข้อความว่าทำรายการนี้ไม่ได้ในสถานะปัจจุบัน
- **ยกเลิก (ก่อนส่งมอบเท่านั้น):** ผู้ยืมและผู้ที่ทำเอกสารแทนยกเลิกของตนได้ (ไม่ต้องระบุเหตุผล) ผู้อนุมัติของสาขายกเลิกเอกสารของคนอื่นได้ที่สถานะส่งแล้วขึ้นไป โดย **ต้องระบุเหตุผลอย่างน้อย 5 ตัวอักษร** (และผู้ยืมได้รับแจ้ง)
  **ADMIN ยกเลิกเอกสารของคนอื่นไม่ได้ในตอนนี้ [ยังรอ CEO ตัดสิน]** (ยกเลิกของตนเองได้) หลังส่งมอบแล้วยกเลิกไม่ได้
- **การแจ้งเตือน:** ส่งหลังบันทึกผลสำเร็จเท่านั้น ถ้าส่งไม่สำเร็จจะไม่ยกเลิกผลที่บันทึก (มีบรรทัดเตือนใน log) N1 อาจารย์ (อีเมล + ในระบบ) · N2 ผู้อนุมัติของสาขา (ในระบบถึงทุกคน อีเมลเฉพาะผู้ดูแลคลัง ไม่ถึงสาขาอื่น ไม่ถึงคนที่ไม่มีสาขา) ·
  N3 ผลการตัดสินถึงผู้ยืม (ไม่แจ้งคนที่ตัดสินเอง) **อีเมลต้องมี queue worker ทำงานอยู่**
- **ค่าที่ปรับได้** อยู่ใน `config/loans.php` (ไม่มีหน้าจอ แก้แล้วต้อง deploy): ยืมมาตรฐาน 7 วัน, นานสุด 30 วัน, ขอล่วงหน้าไม่เกิน 30 วัน, ไม่เกิน 20 รายการต่อเอกสาร, ลิงก์อาจารย์ 72 ชั่วโมง

**Audit Log ที่เกิดขึ้น:** `LOAN_CREATE`, `LOAN_SUBMIT`, `LOAN_ADVISOR_APPROVE/REJECT`, `LOAN_APPROVE/REJECT`, `LOAN_SELF_APPROVE/SELF_REJECT`, `LOAN_CANCEL`, และ `LAB_ASSIGN` / `PROFILE_APPROVAL_FIELDS_CHANGE` (เปลี่ยนสาขา)
ทุกแถวมีผู้ทำ เวลา และ IP (ไม่เก็บชื่อ เบอร์ หรือรหัสนิสิตในรายละเอียด)

**ลำดับ deploy ขั้น 2 (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน หลัง CEO อนุมัติ ทำตามลำดับเท่านั้น)**

1. สำรองฐานข้อมูล และตรวจว่า deploy ขั้น 1 ครบแล้ว (ตาราง `loan_assets`, `loan_movements` และสิทธิ์ `loan.*` อยู่ในระบบ)
2. `php artisan migrate` (ไฟล์ `2026_11_05_000001_create_loans_tables.php` สร้างตาราง `loans`, `loan_lines`, `loan_approvals` ว่างเปล่า ไม่แตะตารางเดิม; เพิ่ม `loans.submitted_at` และ `loan_lines.qty_approved`)
3. **รัน `docker/mariadb/restrict_app_grants.sql` ซ้ำ ทุกฐานข้อมูล** (รวมฐานทดสอบ `cmis_testing`) ไม่ต้องแก้ไฟล์สคริปต์: ตารางใหม่ทั้งสามเป็นสิทธิ์ปกติ (SELECT/INSERT/UPDATE/DELETE) ไม่ใช่ append-only
   ส่วน `loan_movements` ยังคง SELECT + INSERT เท่านั้น ถ้าลืมขั้นนี้ `cmis_app` จะได้ "command denied" บนตารางใหม่ และเทสต์บน `cmis_testing` จะล้มด้วยข้อความเดียวกัน
4. ไม่ต้องรัน seeder เพิ่ม (ขั้น 2 ไม่เพิ่มรหัสสิทธิ์) ถ้าเครื่องนั้นยังไม่เคยรัน `PermissionSeeder` ตามขั้น 1 ให้รันก่อน (รันซ้ำปลอดภัย)
5. ตรวจว่า **ผู้ที่ต้องยืมหรืออนุมัติทุกคนมี `lab_id`** (หน้าจัดการผู้ใช้) และ **ทุกสาขามีผู้อนุมัติ (นักวิทยาศาสตร์หรือผู้ดูแลคลัง) ที่ active อย่างน้อย 1 คน** และอาจารย์ที่ปรึกษาของนิสิตมีบทบาท ADVISOR และอีเมลที่ใช้ได้
6. ทดลองหนึ่งรอบด้วยบัญชีทดสอบของสาขา: ขอยืม → (นิสิต) อาจารย์อนุมัติ → ผู้อนุมัติอนุมัติ → ตรวจ Audit Log และคิว "รอการอนุมัติ" แล้วยกเลิกเอกสารทดสอบ
- **ถ้าเปิดหน้าต่าง ๆ แล้วขึ้น "command denied"** = ข้ามขั้นที่ 3 ให้รันสคริปต์ grants กับทุกฐานแล้วลองใหม่
- **ถ้าผู้ใช้บอกว่า "ยืมไม่ได้/ไม่เห็นเมนู"** ตรวจตามลำดับ: มี `lab_id` หรือไม่ → มีบทบาทที่ถือ `loan.create` หรือไม่ → โปรไฟล์ครบ (ประเภทบุคคล และอาจารย์สำหรับนิสิต) หรือไม่
- **ถ้าคำขอค้างไม่มีใครอนุมัติ** ดูการแจ้งเตือน "สาขาไม่มีผู้อนุมัติ" ที่ ADMIN ได้รับ แล้วตั้งสาขาให้นักวิทยาศาสตร์/ผู้ดูแลคลังของสาขานั้น

**คู่มือผู้ใช้อย่างย่อ (ขั้น 2)**
- **ผู้ยืม (นิสิต อาจารย์ เจ้าหน้าที่):** เมนู "ยืม-คืนวัสดุ" → "ขอยืม" เลือกของที่พร้อมให้ยืมของสาขาตน ใส่จำนวนเต็ม วัตถุประสงค์ วันรับของ และกำหนดคืน แล้ว "บันทึกฉบับร่าง" (แก้ได้) หรือ "บันทึกและส่งคำขอ"
  ติดตามสถานะที่ "ของที่ฉันยืม" ส่งแล้วแก้ไม่ได้ ยกเลิกได้ก่อนส่งมอบ การขอไม่ได้จองของ จำนวนจะถูกตรวจอีกครั้งตอนอนุมัติ
  ถ้าขึ้น "รอกำหนดสาขา" ให้ติดต่อ ADMIN (ถ้ายังไม่เคยเลือกสาขา เลือกได้หนึ่งครั้งในหน้าข้อมูลส่วนตัว)
- **อาจารย์ที่ปรึกษา:** เปิดลิงก์ในอีเมล (ใช้ได้ 72 ชั่วโมง ครั้งเดียว) หรือเข้า "ยืม-คืนวัสดุ" → "รอการอนุมัติ" เลือก อนุมัติ หรือ ไม่อนุมัติ (ต้องใส่เหตุผล)
- **นักวิทยาศาสตร์/ผู้ดูแลคลัง (ผู้อนุมัติ):** "รอการอนุมัติ" → เปิดเอกสาร ตรวจรายการและจำนวนพร้อมให้ยืม แล้วอนุมัติ (เว้นช่องจำนวนไว้ = ตามที่ขอ หรือกรอกน้อยกว่า + เหตุผล) หรือไม่อนุมัติ + เหตุผล
  ถ้าเป็นคำขอของตนเอง ระบบอนุญาตแต่บันทึกไว้ว่าผู้ขอ = ผู้อนุมัติ · "รายการของสาขา" (ผู้ดูแลคลัง) กรองดูเอกสารทั้งหมดของสาขาได้
- **เจ้าหน้าที่เคาน์เตอร์ (ผู้ถือสิทธิ์ส่งมอบ):** ในหน้า "ขอยืม" ค้นชื่อผู้ยืมของสาขาตน แล้วทำคำขอแทน (สถานะผู้ยืมและอาจารย์ใช้ตามโปรไฟล์ผู้ยืม แก้เองไม่ได้ และทำแทนแล้วอนุมัติเองไม่ได้)
  ผู้ยืมต้องมีสาขา ถ้าผู้ยืมไม่มีสาขาจะทำแทนไม่ได้

## 3. Audit Log

ทุกการกระทำสำคัญในระบบ (ล็อกอิน, สร้าง/แก้ไข/อนุมัติ/ปฏิเสธ ทุกประเภทเอกสาร) ถูกบันทึกไว้ใน Audit Log
โดยอัตโนมัติ **แก้ไขหรือลบไม่ได้แม้แต่ ADMIN เอง** (append-only เหมือนบัญชีคุมวัสดุ) เข้าถึงได้ผ่านสิทธิ์
`audit.view` — ปัจจุบันยังไม่มีหน้าจอค้นหา/กรอง Audit Log โดยเฉพาะ (ต้องดูผ่านฐานข้อมูลโดยตรงหรือรอ UI
เพิ่มเติมในอนาคต) — บันทึกไว้เป็นข้อจำกัดที่ทราบอยู่แล้ว

## 4. การตรวจสอบความสมบูรณ์ของบัญชีคุม (Hash Chain)

บัญชีคุมวัสดุทุกแถวเชื่อมโยงกันด้วย hash chain (คล้ายหลักการของ blockchain แบบง่าย) เพื่อรับประกันว่าไม่มี
ใครแก้ไขประวัติย้อนหลังได้โดยไม่ถูกตรวจจับ

- **ตรวจสอบด้วยตนเอง**: รันคำสั่ง `php artisan ledger:verify` (ผ่าน SSH/RDP เข้าเซิร์ฟเวอร์ หรือให้ผู้ดูแล
  ระบบเทคนิครันให้) จะรายงานว่า chain สมบูรณ์ 100% หรือพบจุดที่ขาดหาย/ถูกแก้ไข
- **ตรวจสอบอัตโนมัติ**: ระบบตรวจสอบให้เองทุกชั่วโมง ถ้าพบความผิดปกติจะ**ส่งอีเมลแจ้งเตือน ADMIN ทุกคน
  ทันที** (ไม่มีการแจ้งเตือนในระบบ เฉพาะอีเมลเท่านั้น เนื่องจากเป็นเหตุการณ์ร้ายแรงที่ควรรู้แม้ไม่ได้
  เปิดระบบอยู่)

ถ้าพบว่า chain ไม่สมบูรณ์ **ควรถือเป็นเหตุการณ์ด้านความปลอดภัยข้อมูล (security incident)** — ดูขั้นตอน
รับมือใน `pdpa_breach_response_plan.md` ประกอบ (แม้ชื่อไฟล์จะเน้น PDPA แต่ขั้นตอนแจ้งเหตุ/ทีมรับผิดชอบใช้
ร่วมกันได้กับเหตุการณ์ด้านความปลอดภัยข้อมูลทุกประเภท)

## 5. การแจ้งเตือนอัตโนมัติ

ระบบมีงานตรวจสอบอัตโนมัติที่ทำงานเป็นระยะ ไม่ต้องตั้งค่าอะไรเพิ่มถ้าติดตั้งตามคู่มือ (`docs/
iis_installation_guide.md` §8):

| รายการตรวจสอบ | ความถี่ | แจ้งใคร |
|---|---|---|
| ยอดคงเหลือต่ำกว่าจุดสั่งซื้อ | ทุกวัน | ผู้มีสิทธิ์จัดการทะเบียนสารเคมี (LAB_MANAGER, AUDITOR) |
| ภาชนะใกล้หมดอายุ (90/30/7 วัน) | ทุกวัน (แจ้งครั้งเดียวต่อช่วง) | ผู้ถือสิทธิ์จัดการทะเบียนสารเคมีหรือขอทำลาย (LAB_MANAGER, AUDITOR, ADMIN — SCIENTIST ไม่ได้รับแล้ว) |
| ภาชนะเปิดใช้เกินอายุการใช้งานหลังเปิด | ทุกวัน | ผู้ถือสิทธิ์จัดการทะเบียนสารเคมีหรือขอทำลาย (LAB_MANAGER, AUDITOR, ADMIN) |
| ความสมบูรณ์ของ Hash Chain | ทุกชั่วโมง | ADMIN ทุกคน (ทางอีเมลเท่านั้น) |

## 6. PDPA — สิทธิ์ของเจ้าของข้อมูลและหน้าที่ผู้ดูแลระบบ

- ผู้ใช้ทุกคนมีสิทธิ์ดู/ขอสำเนาข้อมูลส่วนตัวของตนเองผ่านเมนู "ข้อมูลของฉัน" ด้วยตนเอง (ไม่ต้องผ่าน ADMIN)
- **การลบ/ปกปิดข้อมูลผู้ใช้ที่พ้นสภาพ**: รันคำสั่ง `php artisan users:pseudonymize {user}` (ระบุ ID หรือ
  username ของผู้ใช้ที่ต้องการ) — ระบบจะเขียนทับชื่อ-นามสกุล, username, อีเมล, เบอร์โทร, รหัสนิสิต/พนักงาน
  ด้วยค่าที่ไม่สามารถระบุตัวตนได้ แต่**คงประวัติการทำธุรกรรม (ใบเบิก, บัญชีคุม) ไว้ครบ** เพื่อรักษาความ
  ถูกต้องของบัญชีคุมวัสดุ (ห้ามลบแถวใน ledger ไม่ว่ากรณีใด) — คำสั่งนี้มีการถามยืนยันก่อนทำงานเสมอ (ป้องกัน
  การรันผิดพลาด) และ**ไม่มีการรันอัตโนมัติตามกำหนดเวลา** (ต้องรอนโยบายระยะเวลาการเก็บรักษาข้อมูลที่ชัดเจน
  จากมหาวิทยาลัย/คณะก่อน — ดู `pdpa_breach_response_plan.md` และ CLAUDE.md's Known open items)
- ถ้าเกิดเหตุข้อมูลรั่วไหล ให้ปฏิบัติตามขั้นตอนใน `pdpa_breach_response_plan.md` ทันที (มีกำหนดแจ้ง
  สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ภายใน 72 ชั่วโมงตามกฎหมาย)

## 7. การสำรองและกู้คืนข้อมูล

ดูรายละเอียดฉบับเต็มที่ `docs/backup_restore_runbook.md` — สรุปสิ่งที่ ADMIN ควรรู้:

- ระบบสำรองข้อมูลแบบเต็มทุกวัน + บันทึกการเปลี่ยนแปลงต่อเนื่อง (binlog) ทำให้กู้คืนย้อนไปยังจุดเวลาใดก็ได้
  ระหว่างการสำรองสองครั้งล่าสุด (RPO ≤ 15 นาที)
- **ทดสอบการกู้คืนเป็นระยะ** (drill) เพื่อยืนยันว่ากลไกยังทำงานถูกต้อง — มีสคริปต์อัตโนมัติที่กู้คืนลง
  ฐานข้อมูลแยกต่างหาก **ไม่กระทบข้อมูลจริงเลย** ใช้ทดสอบได้บ่อยเท่าที่ต้องการ
- ถ้าเกิดเหตุต้องกู้คืนจริง เป็นงานของทีมเทคนิค/ผู้ดูแลระบบฐานข้อมูลโดยตรง ไม่ใช่งานที่ทำผ่านหน้าเว็บ CMIS

## 8. สำหรับผู้ตรวจสอบ (AUDITOR)

บทบาท AUDITOR ถูกปรับบทบาทเมื่อ 2026-09-21 (ตามคำสั่ง CEO): **ไม่ใช่บทบาทอ่านอย่างเดียวแล้ว** แต่เป็นผู้ดูแลคลัง
ประจำสาขา (ชื่อแสดง "ผู้ดูแลคลัง") ที่ถืออยู่ในสิทธิ์**เท่ากับ LAB_MANAGER ทุกประการ** (กำหนดแยกต่อผู้ใช้ได้):

- ดูใบขอเบิกทั้งหมด, พิจารณาใบขอเบิก, **จ่าย/รับคืนของตามใบเบิก (สาขาและชนิดที่รับผิดชอบ)**, อนุมัติจ่ายเกิน 10%
- รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลายและอนุมัติทำลาย/ตัดจำหน่าย, อนุมัติปรับปรุงยอด, ดูบัญชีคุม
- จัดการทะเบียนสารเคมี/ผังจัดเก็บ/สมาชิกที่เบิกได้, จัดการคลัง IMS, ดูรายงาน
- **ไม่มี**: ตรวจสอบ Hash Chain (`ledger.verify`) และ Audit Log (`audit.view`) — ถอนออกจาก AUDITOR แล้ว (LAB_MANAGER ก็ไม่มี) ปัจจุบันเป็นของ ADMIN เท่านั้น
- ขอบเขตการทำงานจำกัดตามสาขาของผู้ใช้ (ดู `User::isBranchManager()`)

## 9. การบูตสแตรปบัญชีผู้ดูแลระบบคนแรก

ระบบใหม่ (หรือฐานข้อมูลที่เพิ่งกู้คืน/ติดตั้งใหม่) จะ**ไม่มี ADMIN คนใดเลย** — เป็นสถานการณ์ไก่กับไข่ที่ต้อง
แก้ด้วยมือครั้งเดียว:

1. ให้ผู้ที่จะเป็น ADMIN คนแรกล็อกอินผ่านระบบตามปกติ (ข้อ 1 ของคู่มือผู้ใช้) — จะไปค้างที่หน้า "รอผู้ดูแล
   ระบบกำหนดสิทธิ์การใช้งาน" เป็นธรรมดา เพราะยังไม่มีใครมอบสิทธิ์ให้ได้เลยตอนนี้
2. ให้ผู้ดูแลระบบเทคนิค (ผู้มีสิทธิ์เข้าเซิร์ฟเวอร์โดยตรง) รันคำสั่งนี้ผ่าน `php artisan tinker`:
   ```php
   $user = App\Models\User::where('username', '<username ของคนที่ล็อกอินไว้>')->firstOrFail();
   $user->roles()->attach(App\Models\Role::where('code', 'ADMIN')->firstOrFail());
   ```
3. ให้ผู้ใช้คนนั้นรีเฟรชหน้าเว็บ (หรือล็อกอินใหม่) — จะเห็นเมนู "ผู้ใช้งานและสิทธิ์" ปรากฏขึ้น และสามารถ
   มอบสิทธิ์ให้ผู้ใช้คนอื่น ๆ ต่อผ่านหน้าเว็บได้ตามปกติ (ข้อ 1) **ไม่ต้องใช้วิธีนี้ซ้ำอีก**
