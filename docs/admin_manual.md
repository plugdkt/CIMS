# คู่มือผู้ดูแลระบบ CMIS (สำหรับบทบาท ADMIN และ AUDITOR)

เอกสารนี้สำหรับผู้ดูแลระบบ (ADMIN) และผู้ตรวจสอบ (AUDITOR) — ครอบคลุมงานที่ไม่มีในคู่มือผู้ใช้ทั่วไป
(`docs/user_manual.md`) เช่น การกำหนดสิทธิ์ผู้ใช้, การจัดการห้องปฏิบัติการ, การตรวจสอบความสมบูรณ์ของ
บัญชีคุม, และงานที่เกี่ยวข้องกับ PDPA

> **ข้อควรทราบสำคัญ**: บทบาท ADMIN **ไม่มีสิทธิ์แตะต้องบัญชีคุมวัสดุ (ledger) เลย** ไม่ว่าจะเป็นการรับเข้า
> จ่ายออก ปรับปรุงยอด หรือทำลาย — เป็นการออกแบบตั้งใจตาม spec §3 (Separation of Duties) เพื่อป้องกันไม่ให้
> ผู้ดูแลระบบคนเดียวมีอำนาจทั้งด้านระบบและด้านสต๊อกพร้อมกัน ถ้าต้องจัดการเรื่องสต๊อกจริง ต้องให้บัญชีที่มี
> บทบาท SCIENTIST/LAB_MANAGER ดำเนินการแทน

## 1. การกำหนดสิทธิ์ผู้ใช้งาน (Role Provisioning)

ระบบยืนยันตัวตนกลาง (MEDSCI ACC) รู้แค่ "ผู้ใช้นี้คือใคร" — **ไม่รู้จักบทบาทของ CMIS เลย** ผู้ใช้ทุกคนที่
ล็อกอินครั้งแรกจะไม่มีสิทธิ์ใด ๆ จนกว่า ADMIN จะกำหนดให้ (deny-by-default)

1. เมนู "ผู้ใช้งานและสิทธิ์" (`/admin/users`)
2. ค้นหาผู้ใช้ด้วยชื่อหรือ username
3. เลือกบทบาทที่ต้องการมอบให้ (เลือกได้มากกว่า 1 บทบาทต่อคน ถ้าจำเป็น เช่น คนที่เป็นทั้ง SCIENTIST และ
   ADVISOR)

**ตารางบทบาทและสิทธิ์โดยสรุป**:

| บทบาท | สิทธิ์หลัก |
|---|---|
| `STUDENT` | สร้างใบขอเบิก, ดูใบขอเบิกของตนเอง, ดูทะเบียนสารเคมี |
| `STAFF` | เหมือน STUDENT (แต่ไม่มีขั้นตอนอาจารย์ที่ปรึกษา) |
| `ADVISOR` | อนุมัติใบขอเบิกของนิสิตในความดูแล |
| `SCIENTIST` | พิจารณาใบขอเบิก, จ่ายของ, รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลาย/ตัดจำหน่าย, ดูรายงาน |
| `LAB_MANAGER` | อนุมัติปรับปรุงยอด/ทำลาย, จัดการทะเบียนสารเคมี/ผังจัดเก็บ, ดูรายงาน |
| `ADMIN` | จัดการผู้ใช้/สิทธิ์/ห้องปฏิบัติการ/หน่วยนับ, ตรวจสอบ Hash Chain, เข้าถึง Audit Log |
| `AUDITOR` | อ่านอย่างเดียวทั้งระบบ (ใบเบิก, บัญชีคุม, รายงาน) + Audit Log |

**หมายเหตุ**: ผู้ใช้ที่มีสิทธิ์เกี่ยวข้องกับสต๊อก (SCIENTIST) กับผู้อนุมัติปรับปรุงยอด (LAB_MANAGER) ควรเป็น
คนละคนกันในทางปฏิบัติ แม้ระบบจะไม่ได้บังคับห้ามคนเดียวถือทั้งสองบทบาทตรง ๆ — แต่ระบบจะบังคับว่า **ผู้อนุมัติ
ปรับปรุงยอด/ทำลาย ต้องไม่ใช่คนเดียวกับผู้สร้างรายการนั้น** เสมอ (ตรวจสอบที่ระดับ transaction จริง ไม่ใช่แค่
ที่หน้าจอ)

## 2. การจัดการห้องปฏิบัติการ (Labs)

เมนู "ห้องปฏิบัติการ" (`/admin/labs`) — เพิ่ม/แก้ไขรหัสและชื่อห้องปฏิบัติการ จำเป็นก่อนที่จะมีใครสร้างใบ
รับของ (GRN) หรือกำหนดผังจัดเก็บได้ (ทุกใบรับของต้องผูกกับห้องปฏิบัติการหนึ่งห้องเสมอ)

## 3. Audit Log

ทุกการกระทำสำคัญในระบบ (ล็อกอิน, สร้าง/แก้ไข/อนุมัติ/ปฏิเสธ ทุกประเภทเอกสาร) ถูกบันทึกไว้ใน Audit Log
โดยอัตโนมัติ **แก้ไขหรือลบไม่ได้แม้แต่ ADMIN เอง** (append-only เหมือนบัญชีคุมวัสดุ) เข้าถึงได้ผ่านสิทธิ์
`audit.view` — ปัจจุบันยังไม่มีหน้าจอค้นหา/กรอง Audit Log โดยเฉพาะ (ต้องดูผ่านฐานข้อมูลโดยตรงหรือรอ UI
เพิ่มเติมในอนาคต) — บันทึกไว้เป็นข้อจำกัดที่ทราบอยู่แล้ว

## 4. การตรวจสอบความสมบูรณ์ของบัญชีคุม (Hash Chain)

บัญชีคุมวัสดุทุกแถวเชื่อมโยงกันด้วย hash chain (คล้ายหลักการของ blockchain แบบง่าย) เพื่อรับประกันว่าไม่มี
ใครแก้ไขประวัติย้อนหลังได้โดยไม่ถูกตรวจจับ

- **ตรวจสอบด้วยตนเอง**: รันคำสั่ง `php artisan ledger:verify` (ผ่าน SSH/RDP เข้าเซิร์ฟเวอร์ หรือให้ผู้ดูแล
  ระบบเทคนิครันให้) จะรายงานว่า chain สมบูรณ์ 100% หรือพบจุดที่ขาดหาย/ถูกแก้ไข
- **ตรวจสอบอัตโนมัติ**: ระบบตรวจสอบให้เองทุกชั่วโมง ถ้าพบความผิดปกติจะ**ส่งอีเมลแจ้งเตือน ADMIN ทุกคน
  ทันที** (ไม่มีการแจ้งเตือนในระบบ เฉพาะอีเมลเท่านั้น เนื่องจากเป็นเหตุการณ์ร้ายแรงที่ควรรู้แม้ไม่ได้
  เปิดระบบอยู่)

ถ้าพบว่า chain ไม่สมบูรณ์ **ควรถือเป็นเหตุการณ์ด้านความปลอดภัยข้อมูล (security incident)** — ดูขั้นตอน
รับมือใน `pdpa_breach_response_plan.md` ประกอบ (แม้ชื่อไฟล์จะเน้น PDPA แต่ขั้นตอนแจ้งเหตุ/ทีมรับผิดชอบใช้
ร่วมกันได้กับเหตุการณ์ด้านความปลอดภัยข้อมูลทุกประเภท)

## 5. การแจ้งเตือนอัตโนมัติ

ระบบมีงานตรวจสอบอัตโนมัติที่ทำงานเป็นระยะ ไม่ต้องตั้งค่าอะไรเพิ่มถ้าติดตั้งตามคู่มือ (`docs/
iis_installation_guide.md` §8):

| รายการตรวจสอบ | ความถี่ | แจ้งใคร |
|---|---|---|
| ยอดคงเหลือต่ำกว่าจุดสั่งซื้อ | ทุกวัน | ผู้มีสิทธิ์จัดการทะเบียนสารเคมี (LAB_MANAGER) |
| ภาชนะใกล้หมดอายุ (90/30/7 วัน) | ทุกวัน (แจ้งครั้งเดียวต่อช่วง) | LAB_MANAGER + SCIENTIST |
| ภาชนะเปิดใช้เกินอายุการใช้งานหลังเปิด | ทุกวัน | LAB_MANAGER + SCIENTIST |
| ความสมบูรณ์ของ Hash Chain | ทุกชั่วโมง | ADMIN ทุกคน (ทางอีเมลเท่านั้น) |

## 6. PDPA — สิทธิ์ของเจ้าของข้อมูลและหน้าที่ผู้ดูแลระบบ

- ผู้ใช้ทุกคนมีสิทธิ์ดู/ขอสำเนาข้อมูลส่วนตัวของตนเองผ่านเมนู "ข้อมูลของฉัน" ด้วยตนเอง (ไม่ต้องผ่าน ADMIN)
- **การลบ/ปกปิดข้อมูลผู้ใช้ที่พ้นสภาพ**: รันคำสั่ง `php artisan users:pseudonymize {user}` (ระบุ ID หรือ
  username ของผู้ใช้ที่ต้องการ) — ระบบจะเขียนทับชื่อ-นามสกุล, username, อีเมล, เบอร์โทร, รหัสนิสิต/พนักงาน
  ด้วยค่าที่ไม่สามารถระบุตัวตนได้ แต่**คงประวัติการทำธุรกรรม (ใบเบิก, บัญชีคุม) ไว้ครบ** เพื่อรักษาความ
  ถูกต้องของบัญชีคุมวัสดุ (ห้ามลบแถวใน ledger ไม่ว่ากรณีใด) — คำสั่งนี้มีการถามยืนยันก่อนทำงานเสมอ (ป้องกัน
  การรันผิดพลาด) และ**ไม่มีการรันอัตโนมัติตามกำหนดเวลา** (ต้องรอนโยบายระยะเวลาการเก็บรักษาข้อมูลที่ชัดเจน
  จากมหาวิทยาลัย/คณะก่อน — ดู `pdpa_breach_response_plan.md` และ CLAUDE.md's Known open items)
- ถ้าเกิดเหตุข้อมูลรั่วไหล ให้ปฏิบัติตามขั้นตอนใน `pdpa_breach_response_plan.md` ทันที (มีกำหนดแจ้ง
  สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ภายใน 72 ชั่วโมงตามกฎหมาย)

## 7. การสำรองและกู้คืนข้อมูล

ดูรายละเอียดฉบับเต็มที่ `docs/backup_restore_runbook.md` — สรุปสิ่งที่ ADMIN ควรรู้:

- ระบบสำรองข้อมูลแบบเต็มทุกวัน + บันทึกการเปลี่ยนแปลงต่อเนื่อง (binlog) ทำให้กู้คืนย้อนไปยังจุดเวลาใดก็ได้
  ระหว่างการสำรองสองครั้งล่าสุด (RPO ≤ 15 นาที)
- **ทดสอบการกู้คืนเป็นระยะ** (drill) เพื่อยืนยันว่ากลไกยังทำงานถูกต้อง — มีสคริปต์อัตโนมัติที่กู้คืนลง
  ฐานข้อมูลแยกต่างหาก **ไม่กระทบข้อมูลจริงเลย** ใช้ทดสอบได้บ่อยเท่าที่ต้องการ
- ถ้าเกิดเหตุต้องกู้คืนจริง เป็นงานของทีมเทคนิค/ผู้ดูแลระบบฐานข้อมูลโดยตรง ไม่ใช่งานที่ทำผ่านหน้าเว็บ CMIS

## 8. สำหรับผู้ตรวจสอบ (AUDITOR)

บทบาท AUDITOR มีสิทธิ์**อ่านอย่างเดียว**ทั่วทั้งระบบ ไม่มีปุ่มแก้ไข/อนุมัติใด ๆ ปรากฏให้เห็นเลย:

- ดูใบขอเบิกทั้งหมดของทุกคนได้ (ไม่จำกัดแค่ของตนเอง)
- ดูบัญชีคุมวัสดุทุกรายการ, รันตรวจสอบ Hash Chain ได้ (สิทธิ์เดียวกับ ADMIN สำหรับข้อนี้)
- ดูรายงานทั้ง 6 ประเภทได้ (เหมือน LAB_MANAGER/SCIENTIST)
- เข้าถึง Audit Log ได้ (เหมือน ADMIN)

## 9. การบูตสแตรปบัญชีผู้ดูแลระบบคนแรก

ระบบใหม่ (หรือฐานข้อมูลที่เพิ่งกู้คืน/ติดตั้งใหม่) จะ**ไม่มี ADMIN คนใดเลย** — เป็นสถานการณ์ไก่กับไข่ที่ต้อง
แก้ด้วยมือครั้งเดียว:

1. ให้ผู้ที่จะเป็น ADMIN คนแรกล็อกอินผ่านระบบตามปกติ (ข้อ 1 ของคู่มือผู้ใช้) — จะไปค้างที่หน้า "รอผู้ดูแล
   ระบบกำหนดสิทธิ์การใช้งาน" เป็นธรรมดา เพราะยังไม่มีใครมอบสิทธิ์ให้ได้เลยตอนนี้
2. ให้ผู้ดูแลระบบเทคนิค (ผู้มีสิทธิ์เข้าเซิร์ฟเวอร์โดยตรง) รันคำสั่งนี้ผ่าน `php artisan tinker`:
   ```php
   $user = App\Models\User::where('username', '<username ของคนที่ล็อกอินไว้>')->firstOrFail();
   $user->roles()->attach(App\Models\Role::where('code', 'ADMIN')->firstOrFail());
   ```
3. ให้ผู้ใช้คนนั้นรีเฟรชหน้าเว็บ (หรือล็อกอินใหม่) — จะเห็นเมนู "ผู้ใช้งานและสิทธิ์" ปรากฏขึ้น และสามารถ
   มอบสิทธิ์ให้ผู้ใช้คนอื่น ๆ ต่อผ่านหน้าเว็บได้ตามปกติ (ข้อ 1) **ไม่ต้องใช้วิธีนี้ซ้ำอีก**
