# คู่มือผู้ดูแลระบบ CMIS (สำหรับบทบาท ADMIN และ AUDITOR)

เอกสารนี้สำหรับผู้ดูแลระบบ (ADMIN) และ AUDITOR (ปัจจุบันคือผู้ดูแลคลังสิทธิ์เท่า LAB_MANAGER — ดูหัวข้อ 8) — ครอบคลุมงานที่ไม่มีในคู่มือผู้ใช้ทั่วไป
(`docs/user_manual.md`) เช่น การกำหนดสิทธิ์ผู้ใช้, การจัดการห้องปฏิบัติการ, การตรวจสอบความสมบูรณ์ของ
บัญชีคุม, และงานที่เกี่ยวข้องกับ PDPA

> **ข้อควรทราบสำคัญ**: บทบาท ADMIN **ไม่มีสิทธิ์เขียนบัญชีคุมวัสดุ (ledger) โดยตรง** (ไม่มี `ledger.*` ฝั่งเขียน)
> ดังนั้น **ปรับปรุงยอด (`ledger.adjust`), อนุมัติผลตรวจนับ, อนุมัติการทำลาย/ตัดจำหน่าย
> (`disposal.approve`), นำเข้า/ยืนยันใบรับ IMS (`ims.manage`), อนุมัติใบเบิก (`requisition.approve_scientist`) และจ่าย/คืนของตามใบเบิกไม่ได้** — เป็นการออกแบบตั้งใจตาม spec §3
> (Separation of Duties) **แต่ไม่ได้แปลว่า ADMIN ไม่มีผลต่อบัญชีคุมเลย**: เมื่อ ADMIN ยืนยันใบรับของ (GRN)
> ระบบจะสร้างแถว "รับเข้า" (RECEIVE) ในบัญชีคุมให้ **ทางอ้อม** โดยบันทึกผู้ทำรายการเป็น ADMIN (CEO ตัดสิน E7 2026-10-30)
> ADMIN **ทำได้**: รับของเข้าคลัง (`receiving.manage`), เปิดรอบ/ดำเนินการตรวจนับสต๊อก
> (`stocktake.manage`), ขอทำลาย/ตัดจำหน่าย (`disposal.request`) และตรวจสอบ Hash Chain / ดูคลัง IMS / ดูรายงานแบบอ่านอย่างเดียว
> (CEO ยืนยัน 2026-10-30 ว่าเป็นไปตามระบบ) ส่วนงานที่ ADMIN ไม่มีสิทธิ์ ต้องให้บัญชีที่มีบทบาท LAB_MANAGER/AUDITOR ดำเนินการแทน

## 1. การกำหนดสิทธิ์ผู้ใช้งาน (Role Provisioning)

ระบบยืนยันตัวตนกลาง (MEDSCI ACC) รู้แค่ "ผู้ใช้นี้คือใคร" — **ไม่รู้จักบทบาทของ CMIS เลย** ผู้ใช้ทุกคนที่
ล็อกอินครั้งแรกจะไม่มีสิทธิ์ใด ๆ จนกว่า ADMIN จะกำหนดให้ (deny-by-default)

1. เมนู "ผู้ใช้งานและสิทธิ์" (`/admin/users`)
2. ค้นหาผู้ใช้ด้วยชื่อหรือ username
3. เลือกบทบาทที่ต้องการมอบให้ (เลือกได้มากกว่า 1 บทบาทต่อคน ถ้าจำเป็น เช่น คนที่เป็นทั้ง SCIENTIST และ
   ADVISOR)

**ตารางบทบาทและสิทธิ์โดยสรุป**:

| บทบาท | สิทธิ์หลัก |
|---|---|
| `STUDENT` | สร้างใบขอเบิก, ดูใบขอเบิกของตนเอง, ดูทะเบียนสารเคมี |
| `STAFF` | เหมือน STUDENT (แต่ไม่มีขั้นตอนอาจารย์ที่ปรึกษา) |
| `ADVISOR` | รับอีเมล (ลิงก์ 72 ชั่วโมง) ใบขอเบิกของนิสิตในความดูแล และกดอนุมัติ/ไม่อนุมัติ — **ใบเบิกของนิสิต: อาจารย์อนุมัติแล้วสถานะเป็น "อนุมัติแล้ว" ทันที ไปจ่ายของได้เลย ไม่ต้องผ่านขั้นนักวิทยาศาสตร์/ผู้ดูแลคลังอีก** (CEO ตัดสิน 2026-11-04 แบบ ก.) ยังเป็นประตูกั้นจริงตาม BR-02: นักวิทยาศาสตร์/ผู้ดูแลคลังพิจารณาใบเบิกนิสิตที่อาจารย์ยังไม่อนุมัติไม่ได้ (ไม่อนุมัติ = ใบเบิกจบ); ใบเบิกนิสิตเก่าที่ค้างสถานะ "อาจารย์อนุมัติแล้ว" ยังให้นักวิทยาศาสตร์/ผู้ดูแลคลังตัดสินต่อได้; ผู้เบิกที่ไม่ใช่นิสิตข้ามขั้นอาจารย์ (CEO คืนกฎ 2026-10-30) |
| `SCIENTIST` | **พิจารณา (อนุมัติ/ไม่อนุมัติ) ใบขอเบิกของบุคลากรในสาขาตนได้ทุกชนิด และจ่ายของตามใบที่อนุมัติแล้ว** (CEO กลับกติกา 2026-11-04 — นักวิทยาศาสตร์ทุกคนในสาขาเวียนเป็นเวรกัน ระบบไม่ระบุตัวบุคคล) สร้าง/ดูใบขอเบิกของตนเอง, ดูบัญชีคุม/ทะเบียนวัสดุ, เปิดดูของในคลังกลางสาขา (ไม่เห็นราคา), อนุมัติคำขอยืมและเป็นผู้อนุมัติแทนการปรับยอด/ปลดระวางของให้ยืมของสาขาตน — **ข้ามสาขาไม่ได้ และบัญชีที่ไม่มี `lab_id` ทำสิ่งเหล่านี้ไม่ได้เลย**; **ไม่มี**สิทธิ์รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลาย/ตัดจำหน่าย, ดูรายงาน (ย้ายไปผู้ดูแลคลังเมื่อ 2026-09-21/22) |
| `LAB_MANAGER` | ผู้ดูแลคลังประจำสาขา: พิจารณาใบขอเบิก **และจ่ายของตามใบเบิกได้ (ตั้งแต่ 2026-11-04) เฉพาะสาขาและชนิดที่รับผิดชอบ**, อนุมัติจ่ายเกิน 10%, รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลายและอนุมัติทำลาย/ตัดจำหน่าย, อนุมัติปรับปรุงยอด, ดูบัญชีคุมวัสดุ (`ledger.view`), จัดการทะเบียนสารเคมี/ผังจัดเก็บ/สมาชิกที่เบิกได้ในสาขา, จัดการคลัง IMS (นำเข้า/ยืนยัน), ดูรายงาน |
| `ADMIN` | จัดการผู้ใช้/สิทธิ์/ห้องปฏิบัติการ/หน่วยนับ, ตรวจสอบ Hash Chain, เข้าถึง Audit Log, รับของเข้าคลัง, เปิดรอบ/ดำเนินการตรวจนับสต๊อก, ขอทำลาย/ตัดจำหน่าย, ดูใบขอเบิกทั้งหมด/ทะเบียนวัสดุ/รายงาน/คลัง IMS/หน้ารายการปรับปรุงยอด (ดูอย่างเดียว) (**ไม่อนุมัติใบเบิก ไม่จ่าย/คืนของ ไม่อนุมัติคำขอยืม และไม่เป็นผู้อนุมัติแทนการปรับยอด/ปลดระวางของให้ยืม** — CEO ยืนยัน 2026-11-04; ไม่อนุมัติปรับยอด/ผลตรวจนับ/การทำลาย และไม่นำเข้า/ยืนยัน IMS) |
| `AUDITOR` | **ไม่ใช่บทบาทอ่านอย่างเดียวอีกต่อไป** (ปรับบทบาทเมื่อ 2026-09-21) — เป็นผู้ดูแลคลังประจำสาขาอีกรูปแบบหนึ่ง สิทธิ์เท่า LAB_MANAGER ทุกประการ (ทั้ง LAB_MANAGER และ AUDITOR ไม่มี Audit Log/ตรวจ Hash Chain — เป็นของ ADMIN เท่านั้น) |

**หมายเหตุ**: ระบบยังบังคับที่ระดับ transaction จริง (ไม่ใช่แค่ที่หน้าจอ) ว่า **ผู้อนุมัติปรับปรุงยอด ต้องไม่ใช่
คนเดียวกับผู้สร้างรายการ** และ **ผู้อนุมัติผลตรวจนับ ต้องไม่ใช่ผู้นับรายการที่มีผลต่างนั้น** ส่วน
**การทำลาย/ตัดจำหน่ายไม่มีการแยกผู้ขอ/ผู้อนุมัติ** — ผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) คนเดียวขอและอนุมัติเองได้
(CEO ตัดสินใจแล้ว 2026-09-22 "คนเดียวทำได้จบ" อย่าเข้าใจว่าเป็นช่องโหว่)

### ผู้อนุมัติใบเบิก และการอนุมัติ/จ่ายของตัวเอง (approvals.md K, 2026-11-04) [ร่าง รอ CEO ตรวจ]

- **ใครอนุมัติใบเบิกบุคลากร:** นักวิทยาศาสตร์ **ทุกคน** ในสาขาของใบเบิก (ทุกชนิด รวมสารควบคุม) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR)
  เฉพาะสาขา+ชนิดที่รับผิดชอบ **ADMIN อนุมัติใบเบิกไม่ได้** ทุกบทบาทต้องมี `lab_id` ตรงกับสาขาของใบเบิก (**บัญชีที่ไม่มี `lab_id` อนุมัติ/จ่ายไม่ได้เลย**
  ระบบไม่ถือว่า "ว่าง = ตรงกัน") บัญชี ADMIN ที่ถือบทบาทผู้ดูแลคลังด้วย (Super Admin) จึงถูกจำกัดตามสาขาของตนเมื่อใช้สิทธิ์ผู้ดูแลคลังนี้ — **เปลี่ยนจากเดิมที่ข้ามสาขาได้**
- **ใครจ่ายของ:** นักวิทยาศาสตร์ (สาขาตน ทุกชนิด) และผู้ดูแลคลัง (สาขาตน เฉพาะชนิดที่ถือ; ใบผสมสองชนิดต้องถือทั้งสอง) ADMIN จ่ายไม่ได้
- **ใบเบิกนิสิต:** อาจารย์ที่ปรึกษาอนุมัติแล้ว → "อนุมัติแล้ว" ทันที พร้อมจ่าย (ข้ามขั้นนักวิทยาศาสตร์/ผู้ดูแลคลัง) ระบบแจ้งเตือน "พร้อมจ่ายของ" ไปยังผู้จ่ายของสาขา
- **อนุมัติพร้อมกัน:** ถ้านักวิทยาศาสตร์สองคนกดพร้อมกัน ระบบล็อกแถวและตรวจสถานะซ้ำ คนที่กดก่อนชนะ อีกคนได้ข้อความปฏิเสธ (ไม่มีแถวอนุมัติซ้ำ)
- **อนุมัติ/ไม่อนุมัติ/จ่ายของใบเบิกของตัวเอง "ทำได้" (CEO ตัดสิน ไม่มีกฎห้าม)** แต่ระบบบันทึก Audit Log เป็นการควบคุม:
  - ทุกการตัดสินของนักวิทยาศาสตร์/ผู้ดูแลคลังบันทึก `REQ_APPROVE` หรือ `REQ_REJECT`; ถ้าผู้ขอ = ผู้อนุมัติ บันทึกเป็น **`REQ_SELF_APPROVE` / `REQ_SELF_REJECT`**
    (ฟิลด์ `self_approval = true` ในค่าใหม่ของ log)
  - การจ่ายของที่ผู้จ่ายเป็นผู้ขอ หรือผู้อนุมัติ หรือผู้อนุมัติจ่ายเกิน 10% บันทึก **`REQ_SELF_ISSUE`** (ระบุว่าเป็นกรณีใดใน `issuer_is_requester` / `issuer_is_approver` / `issuer_is_overage_approver`)
  - **รายงาน "ใบเบิกที่ผู้ขอเป็นผู้อนุมัติ/ผู้จ่ายเอง"** (หน้ารายงาน แท็บ `self_approval` กรองตามสาขาและวันที่สร้างใบเบิก; ผู้ดูแลคลังเห็นสาขาตน, ADMIN เห็นทุกสาขา) —
    เป็นหน้าจอเท่านั้น ไม่มีส่งออกไฟล์ **ต้องมีคนเปิดดูเป็นประจำ** ไม่เช่นนั้นการควบคุมนี้ไม่มีผล
  - ใบเบิกที่ ผู้ขอ = ผู้อนุมัติ = ผู้จ่าย และจ่ายเกิน 10% ได้ครบวงจรโดยคนเดียว (ผู้ดูแลคลังถือ `requisition.issue_override`) — CEO รับทราบว่าควบคุมด้วยธง/รายงานอย่างเดียว
- **แจ้งเตือน:** ใบที่รออนุมัติ → แจ้ง "ในระบบ" นักวิทยาศาสตร์ที่ active ทุกคนของสาขา + ผู้ดูแลคลังที่ถือชนิดนั้น; **อีเมลส่งเฉพาะผู้ดูแลคลัง** (ไม่ท่วมกล่องนักวิทยาศาสตร์ เพราะเวียนเวร
  ระบบไม่รู้ว่าใครอยู่เวร) ถ้าไม่มีใครในสาขาอนุมัติได้เลย ระบบแจ้ง ADMIN (`requisition.no_approver`) ให้ไปจัดคนในสาขา เพราะ ADMIN อนุมัติเองไม่ได้
- **ข้อยกเว้นของ "ADMIN อนุมัติไม่ได้":** จริงเฉพาะบัญชีที่ถือบทบาท ADMIN ล้วน ๆ ผู้ใช้ที่ถือ ADMIN ร่วมกับ SCIENTIST หรือผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) อนุมัติ/จ่ายได้ตามสิทธิ์ของบทบาทหลังนั้น **ในสาขาของตนเท่านั้น** (ต้องมี `lab_id`)
- **นักวิทยาศาสตร์เห็นใบเบิกทุกใบของสาขาตนที่ไม่ใช่ "ร่าง"** (ทุกสถานะ ทุกชนิด รวมใบที่ตัดสินแล้ว) เพื่อให้เปิดดูคิวอนุมัติและผลการตัดสินได้ ส่วนผู้ดูแลคลังเห็นเฉพาะชนิดที่ถือ; ใบ "ร่าง" ของผู้อื่นไม่เห็น
- **ตรวจจำนวนใบเบิกนิสิตเก่าที่ค้างสถานะ "อาจารย์อนุมัติแล้ว" ก่อน/หลัง deploy (อ่านอย่างเดียว):** ใบเหล่านี้ยังต้องให้นักวิทยาศาสตร์/ผู้ดูแลคลังตัดสินต่อ ใบนิสิตใหม่จะไม่เข้าสถานะนี้อีก
  ```sql
  SELECT l.code AS lab_code, COUNT(*) AS pending_advisor_approved
  FROM requisitions r JOIN labs l ON l.id = r.lab_id
  WHERE r.status = 'ADVISOR_APPROVED' AND r.requester_status = 'STUDENT'
  GROUP BY l.code ORDER BY l.code;
  ```
  หรือ `php artisan tinker --execute="echo AppModelsRequisition::where('status','ADVISOR_APPROVED')->where('requester_status','STUDENT')->count();"` (ผู้ดูแลที่มีสิทธิ์เป็นผู้รัน) ถ้า > 0 ให้แจ้งผู้ดูแลคลัง/นักวิทยาศาสตร์ของสาขานั้นตัดสินให้เสร็จ
- **ตรวจก่อนใช้งานจริง:** ทุกนักวิทยาศาสตร์และผู้ดูแลคลังมี `lab_id`; ทุกสาขามีนักวิทยาศาสตร์หรือผู้ดูแลคลังที่ active อย่างน้อย 1 คนที่รับผิดชอบแต่ละชนิด
  (หลัง seed สิทธิ์ใหม่ด้วย `php artisan db:seed --class=PermissionSeeder` — รันซ้ำปลอดภัย และ **ไม่ถอน** สิทธิ์อนุมัติ/จ่ายของจากบทบาทเหล่านี้อีกแล้ว)

**หน้า "กรอกข้อมูลเพิ่มเติม"** (CEO อนุมัติ 2026-11-02): บัญชีที่มีบทบาท ADMIN ไม่ต้องกรอกเบอร์โทรและรหัสบุคคล
(เว้นว่างได้ ถ้ากรอกเบอร์ ระบบยังตรวจรูปแบบ) ส่วนช่องอื่นยังต้องกรอกตามเดิม บทบาทอื่นทุกบทบาท (นิสิต/เจ้าหน้าที่/
อาจารย์/ผู้ดูแลคลัง) ยังบังคับกรอกเบอร์และรหัสเหมือนเดิม ระบบตัดสินจากบทบาทที่ ADMIN กำหนดให้ ไม่ใช่ค่าที่ผู้ใช้กรอก

## 2. การจัดการห้องปฏิบัติการ (Labs)

เมนู "ห้องปฏิบัติการ" (`/admin/labs`) — เพิ่ม/แก้ไขรหัสและชื่อห้องปฏิบัติการ จำเป็นก่อนที่จะมีใครสร้างใบ
รับของ (GRN) หรือกำหนดผังจัดเก็บได้ (ทุกใบรับของต้องผูกกับห้องปฏิบัติการหนึ่งห้องเสมอ)

### ใบรับของ (GRN) จำกัดตามสาขา (CEO ตัดสิน 2026-10-30)

- **LAB_MANAGER และ AUDITOR** เห็น/สร้าง/แก้ไข/ยืนยัน/ยกเลิกใบรับของได้ **เฉพาะสาขาวิชา (lab) ของตนเอง**
  (สาขาของผู้ใช้คือ `users.lab_id`) — รายการแสดงเฉพาะใบของสาขาตน, ฟอร์มสร้างให้เลือกได้แค่สาขาตน
  ถ้าส่งสาขาอื่นจะถูกปฏิเสธพร้อมข้อความ "สามารถบันทึกใบรับของได้เฉพาะสาขาวิชาของตนเองเท่านั้น"
- **ADMIN** ทำได้ **ทุกสาขา** (ตามการตัดสิน E7)
- ผู้ใช้ที่ไม่ใช่ ADMIN และ **ไม่มี `lab_id`** จะเห็นข้อความ "บัญชีนี้ยังไม่ได้ผูกสาขาวิชา โปรดติดต่อผู้ดูแลระบบ"
  และไม่เห็นปุ่ม "สร้างใบรับของ"
- **ข้อควรทำก่อน deploy**: ตรวจว่า **ผู้ใช้ LAB_MANAGER/AUDITOR ทุกคนมี `lab_id`** (ผูกสาขาแล้ว) มิฉะนั้น
  จะเปิดใบรับของไม่ได้หลังอัปเดตนี้ (อ้างอิง commit 740318b)

### ผู้ดูแลคลังรายชนิด (ITM-2610-052 เฟส 3) [ร่าง รอ CEO ตรวจ]

ใบเบิกแต่ละใบมีชนิดเดียว (สารเคมี หรือ วัสดุสิ้นเปลือง) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) ทำงานกับใบเบิกได้
เฉพาะ **สาขาของตน และชนิดที่ ADMIN กำหนดให้รับผิดชอบ**

- **กำหนดชนิด:** ADMIN เท่านั้น ที่หน้า "ผู้ใช้งานและสิทธิ์" ใต้ชื่อผู้ดูแลแต่ละคนมีปุ่ม "สารเคมี" / "วัสดุสิ้นเปลือง" / "วัสดุวิทยาศาสตร์ (ยืม-คืน)" (ชนิดที่ 3 เพิ่ม 2026-11-05: ADMIN ต้องติ๊กให้เอง ระบบไม่ให้อัตโนมัติ ดูหัวข้อ "ประเภทวัสดุ 3 ค่า")

  LAB_MANAGER/AUDITOR กำหนดชนิดไม่ได้
- **ค่าเริ่มต้นคือ "ไม่มีสิทธิ์" (deny by default):** ผู้ดูแลที่ไม่มีชนิดเลยจะ **เปิดดูใบเบิกไม่ได้ (403) อนุมัติไม่ได้
  และไม่เห็นใบในหน้าจัดการใบเบิก** จะเห็นข้อความเตือนให้ติดต่อ ADMIN ผู้ดูแลที่เพิ่งได้บทบาทใหม่ต้องให้ ADMIN กำหนดชนิดก่อนใช้งาน
- **ผู้ดูแลชนิดอื่นเห็นใบเป็น 403:** ผู้ดูแลที่ถือเฉพาะวัสดุเปิดดู/พิมพ์ PDF ใบเบิกสารเคมีของสาขาเดียวกันไม่ได้ (และกลับกัน)
  ใบเดิมที่ผสมสองชนิด: ผู้ดูแลที่ถือชนิดใดชนิดหนึ่ง **ดูได้แต่อนุมัติไม่ได้** ต้องถือทั้งสองชนิดจึงอนุมัติได้
- **การอนุมัติจ่ายเกิน 10% (BR-04):** ผู้อนุมัติต้องถือทุกชนิดของใบนั้น
- **การแจ้งเตือน (แก้ 2026-11-04):** ใบที่รออนุมัติแจ้งผู้ดูแลที่ active ของสาขาเดียวกันที่ถือชนิดนั้น (ในระบบ+อีเมล) **และนักวิทยาศาสตร์ทุกคนของสาขา (ในระบบอย่างเดียว)**
  ถ้าไม่มีใครรับผิดชอบ ระบบแจ้ง ADMIN ทุกคน (`requisition.no_approver`) ให้ไปกำหนดชนิดให้ผู้ดูแล/จัดคนในสาขา **ADMIN อนุมัติใบเบิกเองไม่ได้**
- **ชนิดที่ผู้ดูแลถือใช้กับการจ่ายของด้วย (2026-11-04):** ผู้ดูแลจ่ายของได้เฉพาะใบที่ทุกชนิดอยู่ในชนิดที่ตนถือ (ส่วนนักวิทยาศาสตร์ไม่ถูกจำกัดตามชนิด)

  การ **ยืนยันสองขั้นจริง** (ผู้ถูกระบุต้องกดยืนยันเอง) จะทำพร้อมขั้น 2

### โมดูลยืม-คืนวัสดุ ขั้น 2: ขอยืม / อนุมัติ / ยกเลิก (ITM-2610-051) [ร่าง รอ CEO ตรวจ]

ขั้น 2 เพิ่ม **เอกสารยืม** ตั้งแต่ผู้ยืมสร้างคำขอจนถึงสถานะ "อนุมัติแล้ว" หรือ "ไม่อนุมัติ/ยกเลิก" **ยังไม่มีการส่งมอบของ รับคืน ต่อกำหนด และเรื่องเสียหาย/สูญหาย**
(ขั้น 3-4) การอนุมัติ **ยังไม่จองของและยังไม่ตัดจำนวนในทะเบียน** ระบบตรวจจำนวนพร้อมให้ยืมสามจุด คือ ตอนส่งคำขอ ตอนอนุมัติ และ (ขั้น 3) ตอนส่งมอบ

**1) สาขา (`users.lab_id`) ต้องมีก่อนจึงยืมได้ และ ADMIN เป็นผู้ตั้ง**
- สาขาของเอกสาร = สาขาของ **ผู้ยืม** (ไม่ใช่ของคนที่กดทำแทน) และรายการของทุกบรรทัดต้องเป็นของสาขานั้น ข้ามสาขาไม่ได้แม้ ADMIN ทำแทน
- ผู้ใช้ที่ไม่มี `lab_id` (รวม ADMIN ที่ไม่มีสาขา) จะถูกพาไปหน้า **"ยังยืมของไม่ได้: รอกำหนดสาขา"** และอีกฝั่งหนึ่ง ผู้ที่ไม่มีสาขาจะไม่เห็นคิวอนุมัติ/รายการของสาขา
- **ตั้งหรือเปลี่ยนสาขา:** หน้าจัดการผู้ใช้และสิทธิ์ (เมนู "ผู้ใช้และสิทธิ์") ช่องสาขาของแต่ละคน บันทึกใน Audit Log ว่า `LAB_ASSIGN` (ค่าเดิม → ค่าใหม่) นี่เป็น **ทางเดียว** ที่เปลี่ยนสาขาที่ตั้งแล้วได้
- **ล็อกสาขา (`User::labLocked()`):** ผู้ใช้ที่มีสาขาแล้วเปลี่ยนสาขาเองจากหน้า "ข้อมูลส่วนตัว" (complete-profile) **ไม่ได้อีก** (ทุกบทบาทรวม ADMIN; ช่องแสดงแบบอ่านอย่างเดียวพร้อมคำอธิบาย; ค่าที่ส่งมาไม่ตรงกับที่เก็บไว้ถูกปฏิเสธ)
  ผู้ที่ยังไม่มีสาขาเลือกได้ **ครั้งเดียว** (บันทึกใน Audit Log เป็น `PROFILE_APPROVAL_FIELDS_CHANGE` ค่าเดิมว่าง → ค่าใหม่) เหตุผล: สาขาเป็นตัวกำหนดว่าใครอนุมัติและยืมของอะไรได้
  ถ้าคนเลือกสาขาผิด ให้แจ้ง ADMIN แก้ตามข้างบน (เป็นการเปลี่ยนที่ควรมีหลักฐานขอเปลี่ยน เพราะกระทบผู้อนุมัติ)

**2) ใครอนุมัติ (approvals.md K, CEO 2026-11-04) [ร่าง]**
- **ขั้นผู้อนุมัติของสาขา (MANAGER):** ผู้ใช้ที่ใช้งานอยู่ ถือ `loan.approve` และมี `lab_id` **ตรงกับสาขาของเอกสาร** = นักวิทยาศาสตร์ (SCIENTIST) ทุกคนของสาขา (เวียนเวร ระบบไม่ระบุตัวบุคคล) และผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) ของสาขา
  ต้องมีสาขาทุกบทบาท (สาขาว่าง = อนุมัติไม่ได้ ไม่มีกรณี "ว่างเท่ากับว่าง") ข้ามสาขาไม่ได้
- **ADMIN อนุมัติไม่ได้** (ไม่ถือ `loan.approve`) ADMIN ดูเอกสารได้ทุกสาขา แต่ถ้าบัญชีเดียวกันถือ SCIENTIST/ผู้ดูแลคลังด้วยก็อนุมัติได้ **เฉพาะสาขาตนเอง** เหมือนคนอื่น
  ผู้ยืมที่เป็น ADMIN ต้องให้นักวิทยาศาสตร์/ผู้ดูแลคลังของสาขาอนุมัติ ดังนั้นแต่ละสาขาต้องมีผู้อนุมัติที่ active อย่างน้อย 1 คน (ถ้าไม่มี คำขอจะค้าง และระบบแจ้ง ADMIN ทุกคนว่า "มีคำขอยืมแต่สาขาไม่มีผู้อนุมัติ" ให้ตั้งสาขาให้ผู้เกี่ยวข้อง)
- **อนุมัติของตัวเองได้ แต่ต้องมีหลักฐาน:** ถ้าผู้ยืม = ผู้อนุมัติ ระบบอนุญาต และบันทึก Audit Log เป็น `LOAN_SELF_APPROVE` / `LOAN_SELF_REJECT` (ในรายละเอียดมี `self_approval = true`) ผู้ตรวจสอบค้นหาการกระทำสองชนิดนี้ย้อนหลังได้
  (การอนุมัติปกติคือ `LOAN_APPROVE` / `LOAN_REJECT`)
- **ผู้ที่ทำเอกสารแทนผู้ยืม (ผู้ถือ `loan.handout` ที่กรอกให้ที่เคาน์เตอร์) อนุมัติเอกสารนั้นเองไม่ได้** แต่ผู้อนุมัติคนอื่นของสาขาอนุมัติได้
- **ผู้ยืมที่เป็นนิสิต:** ต้องผ่าน **อาจารย์ที่ปรึกษาก่อน** อาจารย์ต้องเป็นคนที่ระบุในเอกสาร (ดึงจากโปรไฟล์นิสิตตอนส่งคำขอแล้วล็อกไว้) ยังใช้งานอยู่ ถือ `loan.approve_advisor` และไม่ใช่ตัวผู้ยืมเอง **ADMIN แทนอาจารย์ไม่ได้**
  ผู้ยืมที่ไม่มีค่าประเภทบุคคล (`person_type` ว่าง) ระบบถือเป็นนิสิต และถ้ายังไม่มีอาจารย์ในโปรไฟล์จะถูกส่งไปกรอกโปรไฟล์ก่อน
  - **[CEO ตัดสินแล้ว 2026-11-05 (`board/approvals.md`)]** หลังอาจารย์อนุมัติ ใบยืมของนิสิต = **"อนุมัติแล้ว" ทันที ไม่มีขั้นผู้อนุมัติของสาขา** (เหมือนใบเบิกของนิสิต) ค่า `student_needs_manager_step` ใน `config/loans.php` เป็น `false` เป็นค่าเริ่มต้นแล้ว
    (ตั้งเป็น `true` = กลับไปเส้นทางสองขั้นเดิม เป็นทางย้อนกลับเท่านั้น ต้อง deploy ใหม่และแก้เทสต์ที่ตรึงค่าใน `LoanStateTest` พร้อมกัน)
  - **ตอนอาจารย์กดอนุมัติ ระบบตรวจซ้ำก่อน "อนุมัติแล้ว"** แบบเดียวกับขั้นผู้อนุมัติ: ของยังพร้อมให้ยืม (ไม่ถูกปลดระวาง/ย้ายสาขา) จำนวนที่ขอไม่เกินจำนวนพร้อมให้ยืม ณ ตอนนั้น และวันคืนยังไม่ผ่าน ถ้าไม่ผ่านข้อใด อาจารย์จะเห็นข้อความให้แจ้งนิสิตสร้างคำขอใหม่/ลดจำนวน
    และระบบ **ไม่บันทึกอะไรเลย** (คำขอยังเป็น "ส่งแล้ว" รออาจารย์) ผลที่ได้เมื่อผ่าน: จำนวนที่อนุมัติ = จำนวนที่ขอทุกบรรทัด, มีเวลาอนุมัติและเวลาที่อาจารย์ลงนาม, ช่อง "ผู้อนุมัติ" ว่าง (ไม่มีผู้อนุมัติของสาขา มีเฉพาะแถวขั้นอาจารย์และ Audit Log `LOAN_ADVISOR_APPROVE`) นิสิตได้รับแจ้ง "อนุมัติแล้ว" และ **ผู้อนุมัติของสาขาไม่ได้รับแจ้ง N2 สำหรับคำขอของนิสิต**
    ถ้าอาจารย์ไม่อนุมัติ → "ไม่อนุมัติ" เก็บเหตุผล และไม่ถือว่าอาจารย์ลงนาม
  - **ใบเก่าที่ค้างสถานะ "อาจารย์อนุมัติแล้ว" (`ADVISOR_APPROVED`)** ยังให้ผู้อนุมัติของสาขาอนุมัติ/ไม่อนุมัติต่อได้ตามเดิม ไม่ต้องย้ายข้อมูล ใบใหม่ของนิสิตจะไม่เข้าสถานะนี้อีก
    **SQL ตรวจสำหรับผู้ดูแลเซิร์ฟเวอร์ (อ่านอย่างเดียว) ก่อนและหลังเปิดใช้:**
    ```sql
    SELECT COUNT(*) FROM loans WHERE status='ADVISOR_APPROVED';
    ```
    ถ้า > 0 ใบเหล่านั้นยังรอผู้อนุมัติของสาขาตัดสิน (ยังเห็นในคิว "รอการอนุมัติ" ของสาขา) ถ้าเป็น 0 ก่อนเปิดใช้ ย่อมไม่มีใบเก่า; หลังเปิดใช้ ตัวเลขนี้ควรลดลงเรื่อย ๆ จนเป็น 0 และไม่เพิ่ม
  - ไม่บังคับว่า "ผู้อนุมัติขั้นผู้ดูแลสาขา ≠ อาจารย์ที่ทำขั้นแรก" (CEO ยกเลิกค่าเริ่มต้นนี้แล้ว): ถ้าอาจารย์ท่านเดียวกันถือสิทธิ์นักวิทยาศาสตร์ของสาขาและอนุมัติทั้งสองขั้น ระบบทำให้ และบันทึก `advisor_also_approver = true` ใน Audit Log ของขั้นหลัง
- **ลิงก์อนุมัติทางอีเมลของอาจารย์ (signed link):** ใช้ได้ **72 ชั่วโมง** ใช้ตัดสินได้ **ครั้งเดียว** (กดซ้ำไม่มีผล) จำกัด **10 ครั้งต่อนาที** (เส้นทางสาธารณะ ไม่ต้องล็อกอิน) ลิงก์ปลอม/แก้ไข/หมดอายุได้ 403
  อีเมลมีเฉพาะเลขเอกสาร รายการของ จำนวน และวันคืน **ไม่มีชื่อ เบอร์โทร หรือรหัสนิสิต** อาจารย์อนุมัติในระบบหลังล็อกอินได้เช่นกัน (หน้า "รอการอนุมัติ")
  ถ้าอาจารย์ไม่มีอีเมลหรือบัญชีถูกปิด ผู้ยืมต้องให้ ADMIN แก้โปรไฟล์/มอบอาจารย์ใหม่ก่อน (อาจารย์ของเอกสารที่ส่งแล้วเปลี่ยนไม่ได้ ให้ยกเลิกแล้วสร้างใหม่)
- **จำนวนที่อนุมัติ:** ใส่น้อยกว่าที่ขอได้ (ต้องระบุเหตุผล) มากกว่าที่ขอไม่ได้ มากกว่าจำนวนพร้อมให้ยืม ณ ตอนนั้นไม่ได้ ปฏิเสธต้องระบุเหตุผล อนุมัติไม่ได้ถ้าวันคืนผ่านไปแล้ว
  ถ้ามีผู้อนุมัติสองคนกดพร้อมกัน **คนแรกชนะ** อีกคนได้ข้อความว่าทำรายการนี้ไม่ได้ในสถานะปัจจุบัน
- **ยกเลิก (ก่อนส่งมอบเท่านั้น):** ผู้ยืมและผู้ที่ทำเอกสารแทนยกเลิกของตนได้ (ไม่ต้องระบุเหตุผล) ผู้อนุมัติของสาขายกเลิกเอกสารของคนอื่นได้ที่สถานะส่งแล้วขึ้นไป โดย **ต้องระบุเหตุผลอย่างน้อย 5 ตัวอักษร** (และผู้ยืมได้รับแจ้ง)
  **ADMIN ยกเลิกเอกสารของคนอื่นไม่ได้ในตอนนี้ [ยังรอ CEO ตัดสิน]** (ยกเลิกของตนเองได้) หลังส่งมอบแล้วยกเลิกไม่ได้
- **การแจ้งเตือน:** ส่งหลังบันทึกผลสำเร็จเท่านั้น ถ้าส่งไม่สำเร็จจะไม่ยกเลิกผลที่บันทึก (มีบรรทัดเตือนใน log) N1 อาจารย์ (อีเมล + ในระบบ) · N2 ผู้อนุมัติของสาขา (ในระบบถึงทุกคน อีเมลเฉพาะผู้ดูแลคลัง ไม่ถึงสาขาอื่น ไม่ถึงคนที่ไม่มีสาขา; **เฉพาะคำขอของผู้ยืมที่ไม่ใช่นิสิต** คำขอของนิสิตไม่ส่ง N2 เพราะอาจารย์อนุมัติแล้วจบ) ·
  N3 ผลการตัดสินถึงผู้ยืม รวมผลอนุมัติ/ไม่อนุมัติจากอาจารย์ (ไม่แจ้งคนที่ตัดสินเอง) **อีเมลต้องมี queue worker ทำงานอยู่**
- **ค่าที่ปรับได้** อยู่ใน `config/loans.php` (ไม่มีหน้าจอ แก้แล้วต้อง deploy): ยืมมาตรฐาน 7 วัน, นานสุด 30 วัน, ขอล่วงหน้าไม่เกิน 30 วัน, ไม่เกิน 20 รายการต่อเอกสาร, ลิงก์อาจารย์ 72 ชั่วโมง

**Audit Log ที่เกิดขึ้น:** `LOAN_CREATE`, `LOAN_SUBMIT`, `LOAN_ADVISOR_APPROVE/REJECT`, `LOAN_APPROVE/REJECT`, `LOAN_SELF_APPROVE/SELF_REJECT`, `LOAN_CANCEL`, และ `LAB_ASSIGN` / `PROFILE_APPROVAL_FIELDS_CHANGE` (เปลี่ยนสาขา)
ทุกแถวมีผู้ทำ เวลา และ IP (ไม่เก็บชื่อ เบอร์ หรือรหัสนิสิตในรายละเอียด)

6. ทดลองหนึ่งรอบด้วยบัญชีทดสอบของสาขา: ขอยืม → (นิสิต) อาจารย์อนุมัติ = "อนุมัติแล้ว" ทันที / (ผู้ยืมที่ไม่ใช่นิสิต) ผู้อนุมัติของสาขาอนุมัติ → ตรวจ Audit Log และคิว "รอการอนุมัติ" แล้วยกเลิกเอกสารทดสอบ
7. (คำตัดสิน CEO 2026-11-05) รัน `SELECT COUNT(*) FROM loans WHERE status='ADVISOR_APPROVED';` **ก่อนและหลังเปิดใช้** บันทึกตัวเลขไว้ ถ้า > 0 ใบเก่ายังอนุมัติต่อโดยผู้อนุมัติของสาขาได้ ไม่ต้องย้ายข้อมูล
- **ถ้าเปิดหน้าต่าง ๆ แล้วขึ้น "command denied"** = ข้ามขั้นที่ 3 ให้รันสคริปต์ grants กับทุกฐานแล้วลองใหม่
- **ถ้าผู้ใช้บอกว่า "ยืมไม่ได้/ไม่เห็นเมนู"** ตรวจตามลำดับ: มี `lab_id` หรือไม่ → มีบทบาทที่ถือ `loan.create` หรือไม่ → โปรไฟล์ครบ (ประเภทบุคคล และอาจารย์สำหรับนิสิต) หรือไม่
- **ถ้าคำขอค้างไม่มีใครอนุมัติ** ดูการแจ้งเตือน "สาขาไม่มีผู้อนุมัติ" ที่ ADMIN ได้รับ แล้วตั้งสาขาให้นักวิทยาศาสตร์/ผู้ดูแลคลังของสาขานั้น

**คู่มือผู้ใช้อย่างย่อ (ขั้น 2)**
- **ผู้ยืม (นิสิต อาจารย์ เจ้าหน้าที่):** เมนู "ยืม-คืนวัสดุ" → "ขอยืม" เลือกของที่พร้อมให้ยืมของสาขาตน ใส่จำนวนเต็ม วัตถุประสงค์ วันรับของ และกำหนดคืน แล้ว "บันทึกฉบับร่าง" (แก้ได้) หรือ "บันทึกและส่งคำขอ"
  ติดตามสถานะที่ "ของที่ฉันยืม" ส่งแล้วแก้ไม่ได้ ยกเลิกได้ก่อนส่งมอบ การขอไม่ได้จองของ จำนวนจะถูกตรวจอีกครั้งตอนอนุมัติ
  ถ้าขึ้น "รอกำหนดสาขา" ให้ติดต่อ ADMIN (ถ้ายังไม่เคยเลือกสาขา เลือกได้หนึ่งครั้งในหน้าข้อมูลส่วนตัว)
- **อาจารย์ที่ปรึกษา:** เปิดลิงก์ในอีเมล (ใช้ได้ 72 ชั่วโมง ครั้งเดียว) หรือเข้า "ยืม-คืนวัสดุ" → "รอการอนุมัติ" เลือก อนุมัติ หรือ ไม่อนุมัติ (ต้องใส่เหตุผล) การอนุมัติของอาจารย์ถือเป็นการอนุมัติสมบูรณ์ ผู้ยืมไปรับของได้ ถ้าของไม่พร้อมหรือวันคืนผ่านไปแล้ว ระบบจะแจ้งและไม่บันทึก ให้แจ้งนิสิตสร้างคำขอใหม่
- **นักวิทยาศาสตร์/ผู้ดูแลคลัง (ผู้อนุมัติ):** "รอการอนุมัติ" (คำขอของนิสิตไม่ผ่านขั้นนี้ ยกเว้นใบเก่าที่ค้างอยู่) → เปิดเอกสาร ตรวจรายการและจำนวนพร้อมให้ยืม แล้วอนุมัติ (เว้นช่องจำนวนไว้ = ตามที่ขอ หรือกรอกน้อยกว่า + เหตุผล) หรือไม่อนุมัติ + เหตุผล
  ถ้าเป็นคำขอของตนเอง ระบบอนุญาตแต่บันทึกไว้ว่าผู้ขอ = ผู้อนุมัติ · "รายการของสาขา" (ผู้ดูแลคลัง) กรองดูเอกสารทั้งหมดของสาขาได้
- **เจ้าหน้าที่เคาน์เตอร์ (ผู้ถือสิทธิ์ส่งมอบ):** ในหน้า "ขอยืม" ค้นชื่อผู้ยืมของสาขาตน แล้วทำคำขอแทน (สถานะผู้ยืมและอาจารย์ใช้ตามโปรไฟล์ผู้ยืม แก้เองไม่ได้ และทำแทนแล้วอนุมัติเองไม่ได้)
  ผู้ยืมต้องมีสาขา ถ้าผู้ยืมไม่มีสาขาจะทำแทนไม่ได้

### โมดูลยืม-คืนวัสดุ: ลำดับ deploy ขั้น 3–5 รวดเดียว (ITM-2610-051) [ร่าง รอ CEO ตรวจ — เพิ่มตาม QA 2026-11-12]

**ให้ deploy ขั้น 3, 4 และ 5 พร้อมกันในรอบเดียว** (โค้ดสามขั้นมาด้วยกันและพึ่งกัน: หน้าเอกสาร/เคาน์เตอร์ของขั้น 3 อ่านตารางของขั้น 4 และรายงานของขั้น 5 อ่านทั้งสองขั้น)
ลำดับ deploy แยกรายขั้นในหัวข้อย่อยด้านล่าง **ใช้อ้างอิงรายละเอียดเท่านั้น** เมื่อ deploy รวมให้ทำตามลำดับนี้ (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน **หลัง CEO อนุมัติ** ทำตามลำดับเท่านั้น):

1. **สำรองฐานข้อมูลก่อน และทดสอบว่าไฟล์สำรองกู้คืนได้** · ตรวจว่า deploy ขั้น 1-2 ครบแล้ว · บันทึกจำนวนแถว `attachments` ต่อ `doc_type` ไว้เทียบ (ขั้น 4 ALTER ENUM ของตารางนี้) · ทำช่วงที่ไม่มีผู้ใช้
2. pull / build โค้ด (`composer install --no-dev --optimize-autoloader` ตาม `docs/iis_installation_guide.md`)
3. `php artisan migrate` **ครั้งเดียว** — จะรัน 3 ไฟล์ตามลำดับ: `2026_11_11_000001_create_loan_due_changes_table` (ขั้น 3), `2026_11_11_000002_create_loan_incidents_table` (ขั้น 4), `2026_11_12_000001_create_loan_notice_log_table` (ขั้น 5)
   ถ้าล้มกลางทาง **หยุด อย่ารันซ้ำ** เก็บข้อความผิดพลาดและแจ้งทีมพัฒนา (DDL ของ MariaDB ย้อนกลับเองไม่ได้; ทางกลับคือกู้จากไฟล์สำรองข้อ 1)
4. **รัน `docker/mariadb/restrict_app_grants.sql` ซ้ำ ทุกฐานข้อมูล** (ไม่ต้องแก้สคริปต์) — ถ้าข้าม หน้าเอกสาร/คิว/การรับคืนชำรุด/งานรายวันจะขึ้น "command denied"
5. **ไม่ต้องรัน seeder** (ขั้น 3-5 ไม่เพิ่มรหัสสิทธิ์)
6. ล้างและสร้าง cache ใหม่ (มี route, view, config และคำสั่ง Artisan ใหม่): `php artisan optimize:clear` แล้ว `php artisan config:cache`, `php artisan route:cache`, `php artisan view:cache` (ตาม `iis_installation_guide.md`)
7. `php artisan queue:restart` — ให้ queue worker โหลดโค้ดใหม่ (อีเมลแจ้งเตือนเป็นงานคิว) แล้วตรวจว่า worker กลับมาทำงาน (`iis_installation_guide.md` §8.2)
8. **ตรวจ scheduler:** Task Scheduler / cron ต้องรัน `php artisan schedule:run` **ทุก 1 นาที** (§8.1) และ `php artisan schedule:list` ต้องเห็น `loans:notify-daily` (07:00), `loans:notify-monthly` (วันที่ 1 07:30), `loans:verify --notify` (ทุกชั่วโมง)
9. ตรวจหลัง deploy: จำนวนแถว `attachments` ต่อ `doc_type` เท่าข้อ 1 · ทุกสาขามีผู้ถือ `loan.asset_approve` ที่ใช้งานอยู่ ≥ 2 คน (SQL ในหัวข้อขั้น 5) · เคาน์เตอร์ทุกคนมี `lab_id` · สแกนไวรัสเปิดอยู่
10. ทดลองหนึ่งรอบด้วยบัญชีและของทดสอบที่ตั้งชื่อชัดเจน: ขอยืม → อนุมัติ → ส่งมอบ → คืนบางส่วน → คืนชำรุด 1 ชิ้น → อีกคนบันทึกผล → เอกสารปิด → เปิดแท็บ "รายงาน" ส่งออก CSV หนึ่งไฟล์ → `php artisan loans:verify` ต้องจบด้วยรหัส 0
    (ไม่รัน `loans:notify-daily` ทดลองบนเครื่องจริง เพราะผู้ใช้จะได้รับข้อความจริง)

### โมดูลยืม-คืนวัสดุ ขั้น 3: ส่งมอบ / รับคืน / ต่อกำหนดคืน (ITM-2610-051) [ร่าง รอ CEO ตรวจ — ยังไม่ commit; ชุดเทสต์เต็ม 2016 ผ่าน ข้าม 2 (2026-11-12 ก่อนรอบแก้ตาม QA; เลขาจะรันใหม่หลังรอบแก้)]

ขั้น 3 ทำให้ยืมครบวงจรปกติ: **ส่งมอบของ → รับคืน (บางส่วนได้) → ปิดเอกสาร**, ต่อกำหนดคืน, พิมพ์ใบยืม, และบล็อกการยืมใหม่เมื่อค้างคืนเกินกำหนด
การรับคืนแบบชำรุด (รอซ่อม) และการบันทึกของสูญหาย **มาในขั้น 4 (ดูหัวข้อถัดไป)**: ถ้าระบบที่ใช้อยู่ยัง deploy ถึงแค่ขั้น 3 และของหายหรือเสียจนใช้ไม่ได้ ให้ **ยังไม่บันทึกรับคืนรายการนั้น** และแจ้งผู้ดูแลคลัง

**1) ใครส่งมอบ/รับคืนได้**
- ผู้ที่ยังใช้งานอยู่ ถือ `loan.handout` **จากบทบาทที่ไม่ใช่ ADMIN** และ `lab_id` **ตรงกับสาขาของเอกสาร** = นักวิทยาศาสตร์และผู้ดูแลคลังของสาขานั้น
  ไม่มีสาขา = ไม่ได้ · ต่างสาขา = ไม่ได้ · **ADMIN อย่างเดียว = ไม่ได้** (แม้อยู่สาขาเดียวกัน) · ADMIN ที่เป็นนักวิทยาศาสตร์/ผู้ดูแลคลังด้วย ทำได้เฉพาะสาขาตน
- หน้า "ส่งมอบ/รับคืน" (แท็บใหม่ในการ์ดยืม-คืน) เห็นได้เมื่อถือ `loan.view_queue` และมีสาขา ADMIN ที่มีสาขา **เห็นแบบอ่านอย่างเดียว** (มีข้อความแจ้ง ไม่มีปุ่ม); ไม่แสดงราคาในหน้าใดของขั้นนี้
- **[รอ CEO ยืนยัน] ผู้ส่งมอบ/รับคืน = ผู้ยืม: ระบบไม่ห้าม แต่บันทึก Audit Log เป็น `LOAN_SELF_HANDOUT` / `LOAN_SELF_RETURN`** (`handler_is_borrower = true`)
  ตามคำสั่ง "ยืม-คืนใช้กติกาเดียวกับใบเบิก" (สเปกเดิม BR-L04 เขียนว่าห้าม) ผู้ตรวจสอบค้นสองรหัสนี้ย้อนหลังได้ รายการปกติคือ `LOAN_HANDOUT` / `LOAN_RETURN`

**2) กติกาส่งมอบและรับคืน**
- ส่งมอบได้เฉพาะเอกสาร "อนุมัติแล้ว" **ทุกรายการพร้อมกัน** (ไม่มีส่งมอบบางส่วน) จำนวน = จำนวนที่อนุมัติ ต้องบันทึกสภาพทุกรายการ (ดี/พอใช้/ชำรุด; "ชำรุด" ต้องมีหมายเหตุ)
  ระบบตรวจจำนวนพร้อมให้ยืมอีกครั้งตอนกดยืนยัน ถ้ารายการใดไม่พอ **ไม่มีรายการใดถูกส่งมอบ** · **วันกำหนดคืนผ่านไปแล้วส่งมอบไม่ได้** (ให้ยกเลิกแล้วทำคำขอใหม่) · ใบยืมของนิสิตที่อาจารย์อนุมัติแล้วส่งมอบได้เลย
- รับคืนทีละส่วนได้ คืนเกินจำนวนที่ค้างไม่ได้ ถ้าสภาพตอนคืน **แย่กว่า** ตอนส่งมอบต้องระบุเหตุผลการสึกหรอ **อย่างน้อย 10 ตัวอักษร** คืนครบทุกรายการ ระบบปิดเอกสารเอง
- **หลังส่งมอบแล้วยกเลิกเอกสารไม่ได้** · ของที่ยังถูกยืมอยู่ปลดระวางไม่ได้ และปรับลดยอดกองต่ำกว่าจำนวนที่ถูกยืมไม่ได้
- สองคนกดพร้อมกัน: คนแรกสำเร็จ อีกคนได้ข้อความว่าทำรายการนี้ไม่ได้ (ทดสอบด้วยกระบวนการจริงพร้อมกัน 50 รายการ ยอดถูกยืมไม่เกินยอดทั้งหมด)

**3) ต่อกำหนดคืน** (ค่าใน `config/loans.php`: `max_renewals` 3, `max_total_days` 60, ครั้งละไม่เกิน `default_loan_days` 7 วัน)
- ผู้ยืม (หรือผู้ทำเอกสารแทน) ขอได้ขณะของยังอยู่กับผู้ยืมและ **ยังไม่เกินกำหนด** (วันกำหนดคืนเองยังขอได้) **ครั้งแรกมีผลทันที** ครั้งถัดไปรอผู้อนุมัติของสาขา (ผู้ถือ `loan.approve` สาขาเดียวกัน; ADMIN ไม่ได้)
  ระหว่างรอ กำหนดคืน **ยังเป็นวันเดิม** มีคำขอรอได้ครั้งละหนึ่งรายการ ไม่อนุมัติต้องระบุเหตุผล คำขอที่ไม่อนุมัติไม่นับเป็นครั้งที่ต่อ
- รวมไม่เกิน 60 วันนับจากวันส่งมอบ (หรือ 2 เท่าของ `max_loan_days` ที่สั้นที่สุดของของในเอกสาร ถ้าน้อยกว่า) ถ้าวันที่ขอเลื่อนผ่านไปแล้วตอนพิจารณา อนุมัติไม่ได้ (ให้ไม่อนุมัติ)
- **[รอ CEO ยืนยัน] ผู้อนุมัติต่อกำหนด = ผู้ยืม: ไม่ห้าม แต่บันทึกเป็น `LOAN_SELF_RENEW_APPROVE` / `LOAN_SELF_RENEW_REJECT`**

**4) เกินกำหนดและการบล็อกยืมใหม่ (BR-L08)**
- "เกินกำหนด" เป็น **ค่าคำนวณ** (ของยังอยู่กับผู้ยืมและวันกำหนดคืนก่อนวันนี้) ไม่ใช่สถานะที่เก็บ ไม่มีงานตามเวลาที่ต้องรัน
- ผู้ยืมที่มีเอกสารเกินกำหนด **มากกว่า 7 วัน** (`overdue_block_days`; เกิน 7 วันพอดียังยืมได้ วันที่ 8 ถูกบล็อก) สร้างและส่งคำขอใหม่ไม่ได้จนกว่าจะคืนของครบ
- **อนุญาตรายกรณี:** ผู้อนุมัติของสาขาผู้ยืมที่ **ไม่ใช่ตัวผู้ยืม** ทำคำขอแทนและระบุเหตุผล **อย่างน้อย 10 ตัวอักษร** ใช้ได้ **คำขอเดียว** (ไม่เก็บสิทธิ์ไว้ที่ใด) บันทึก Audit Log `LOAN_OVERDUE_OVERRIDE`
  (ผู้อนุญาต ผู้ยืม เลขเอกสารที่ค้าง เหตุผล) ทั้งตอนสร้างและตอนส่ง ADMIN อย่างเดียวอนุญาตไม่ได้

**5) ใบยืม (PDF) และหน้าตรวจสอบเอกสาร**
- ปุ่ม "พิมพ์ใบยืม" มีสำหรับผู้ที่เปิดเอกสารได้ (ผู้ยืม เคาน์เตอร์/ผู้อนุมัติของสาขา ADMIN) ฉบับร่างพิมพ์ไม่ได้ ไม่มีราคาในใบยืม
- QR บนใบยืมไปที่ `/verify/{ulid}` (สาธารณะ ไม่ต้องล็อกอิน) แสดง **เลขเอกสาร วันรับของ และสถานะเท่านั้น** ไม่มีชื่อบุคคล สาขา รายการของ หรือวันคืน ฉบับร่างตอบ 404

**6) ตรวจความสมบูรณ์:** `php artisan loans:verify` เพิ่มข้อ (ค) ยอดถูกยืมของแต่ละรายการ = ยอดค้างในเอกสารที่ของยังอยู่กับผู้ยืม ถ้ามีการแก้ตารางด้วยมือจะรายงานว่า
"on-loan quantity differs from the open loan documents" และจบด้วยรหัส 1 (งานรายชั่วโมง `--notify` ส่งอีเมลถึง ADMIN ตามเดิม)

**Audit Log ที่เกิดขึ้นในขั้น 3:** `LOAN_HANDOUT`, `LOAN_SELF_HANDOUT`, `LOAN_RETURN`, `LOAN_SELF_RETURN`, `LOAN_RENEW_REQUEST`, `LOAN_RENEW_APPROVE`, `LOAN_RENEW_REJECT`,
`LOAN_SELF_RENEW_APPROVE`, `LOAN_SELF_RENEW_REJECT`, `LOAN_OVERDUE_OVERRIDE` (ไม่เก็บชื่อ เบอร์ หรือรหัสนิสิตในรายละเอียด)

**การแจ้งเตือน:** คำขอต่อกำหนดที่รออนุมัติ → ผู้อนุมัติของสาขา (ในระบบทุกคน อีเมลเฉพาะผู้ดูแลคลัง) · ผลการพิจารณา → ผู้ยืม ข้อความมีเฉพาะเลขเอกสารและวันที่
**ยังไม่มีการแจ้งเคาน์เตอร์เมื่อเอกสารได้รับอนุมัติ** (โค้ดเขียนไว้แล้วแต่ยังไม่ได้ต่อสาย **รอ CEO ตัดสิน**) เคาน์เตอร์ดูได้จากหน้า "ส่งมอบ/รับคืน" และตัวเลขบนการ์ด · การเตือนใกล้ครบกำหนด/เกินกำหนดรายวันมาในขั้น 5 (`loans:notify-daily` ดูหัวข้อขั้น 5)

**ลำดับ deploy ขั้น 3 (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน หลัง CEO อนุมัติ ทำตามลำดับเท่านั้น)** — ถ้า deploy ขั้น 3-5 รวดเดียว (แนะนำ) ใช้ "ลำดับ deploy ขั้น 3–5 รวดเดียว" ด้านบนแทน

1. สำรองฐานข้อมูล และตรวจว่า deploy ขั้น 1-2 ครบแล้ว
2. `php artisan migrate` (ไฟล์ `2026_11_11_000001_create_loan_due_changes_table.php`: สร้างตาราง `loan_due_changes` ว่างเปล่า และเพิ่ม foreign key สองตัวบน `loan_movements`

**คู่มือผู้ใช้อย่างย่อ (ขั้น 3)**
- **เคาน์เตอร์ (นักวิทยาศาสตร์/ผู้ดูแลคลัง):** "ยืม-คืนวัสดุ" → "ส่งมอบ/รับคืน" เห็นเอกสารของสาขาที่ "รอส่งมอบ" และ "ค้างคืน" ค้นด้วยเลขเอกสารหรือสแกนเลขประจำตัวของ (ถ้าพบฉบับเดียวระบบเปิดให้เลย)
  ส่งมอบ: ตรวจของ เลือกสภาพทุกรายการ กด "ยืนยันการส่งมอบ" · รับคืน: กรอกจำนวนที่คืนครั้งนี้และสภาพ (เว้นว่างรายการที่ยังไม่คืน) กด "บันทึกการรับคืน"
- **ผู้ยืม:** ดูสถานะและกำหนดคืนที่ "ของที่ฉันยืม" (มีป้าย "เกินกำหนด N วัน" และตัวกรอง "เฉพาะที่เกินกำหนด") ขอต่อกำหนดคืนในหน้าเอกสารก่อนเกินกำหนด พิมพ์ใบยืมได้จากหน้าเอกสาร
- **ผู้อนุมัติของสาขา:** "รอการอนุมัติ" มีรายการ "คำขอต่อกำหนดคืนของสาขา" เปิดเอกสารแล้วอนุมัติหรือไม่อนุมัติ (ต้องใส่เหตุผล)

### โมดูลยืม-คืนวัสดุ ขั้น 4: เหตุชำรุด / สูญหาย และการบันทึกผล (ITM-2610-051) [ร่าง รอ CEO ตรวจ — ยังไม่ commit; ชุดเทสต์เต็ม 2016 ผ่าน ข้าม 2 (2026-11-12 ก่อนรอบแก้ตาม QA; เลขาจะรันใหม่หลังรอบแก้); มีกติกาที่ติดป้าย "รอ CEO ยืนยัน" 5 ข้อ]

ขั้น 4 เปิดการ **รับคืนแบบชำรุดและการบันทึกของสูญหาย** (ที่ขั้น 3 เขียนว่า "ยังไม่มี") ระบบ **บันทึกผลที่ผู้บริหารตัดสินนอกระบบเท่านั้น**
ไม่มีขั้นตอนเรียกเก็บเงิน ไม่รับเงิน และไม่คำนวณค่าชดใช้ให้ใคร

**1) บันทึกเหตุ (หน้ารับคืน)**
- ผู้บันทึก = ผู้ที่รับคืนได้ตามขั้น 3 (นักวิทยาศาสตร์/ผู้ดูแลคลังของสาขาเอกสาร; ADMIN อย่างเดียวไม่ได้)
- แถวเดียวกันกรอกได้สามส่วน: **คืนใช้งานได้** · **ชำรุด** · **สูญหาย** รวมกันต้องไม่เกินจำนวนที่ค้าง ถ้ากรอกชำรุดหรือสูญหายต้องระบุ **"สิ่งที่เกิดขึ้น" อย่างน้อย 10 ตัวอักษร**
  (บรรยายเฉพาะสภาพของ/เหตุการณ์ **ห้ามใส่ข้อมูลสุขภาพหรือข้อมูลส่วนบุคคลของใคร**)
- แต่ละส่วนที่ชำรุด/สูญหายกลายเป็น **"เหตุ" หนึ่งรายการ สถานะ "รอบันทึกผล"** ของจำนวนนั้นย้ายจาก "ถูกยืม" ไปเป็น **"ไม่พร้อมใช้"** จึง **ยังไม่ถูกนำไปให้ยืม**
- **เอกสารยังไม่ปิดจนกว่าเหตุทุกรายการจะบันทึกผลครบ (BR-L12)** แม้ของกลับมาครบแล้ว เมื่อบันทึกผลรายการสุดท้ายและไม่มีของค้าง ระบบปิดเอกสารเอง
- **[รอ CEO ยืนยัน] เอกสารที่ของกลับมาครบ (หรือบันทึกชำรุด/สูญหายครบ) แต่รอผลของเหตุ ไม่นับเป็น "เกินกำหนด" และไม่บล็อกผู้ยืมจากการยืมใหม่**
  (ถือว่ารอการตัดสินของสาขา ไม่ใช่รอผู้ยืม) ถ้ายังมีของค้างกับผู้ยืมแม้ชิ้นเดียว ยังนับเกินกำหนดตามเดิม

**2) บันทึกผล (เมนู "ส่งมอบ/รับคืน" → ลิงก์ "เหตุเสียหาย/สูญหาย")**
- ผู้บันทึกผล = ผู้ที่ยังใช้งานอยู่ ถือ `loan.asset_approve` (นักวิทยาศาสตร์และผู้ดูแลคลัง) **สาขาเดียวกับเอกสาร** และ **ไม่ใช่** ผู้บันทึกเหตุ / ผู้ยืม / ผู้ทำเอกสารแทนผู้ยืม
  ดังนั้น **แต่ละสาขาต้องมีผู้ถือสิทธิ์นี้อย่างน้อย 2 คน** มิฉะนั้นเหตุที่คนหนึ่งบันทึกจะไม่มีใครบันทึกผลได้
- **[รอ CEO ยืนยัน] ADMIN อย่างเดียวบันทึกผลไม่ได้และแนบไฟล์ไม่ได้ (ดูได้ทุกสาขา)** ต่างจากข้อความเดิมในแผนงานที่ว่า "ADMIN ผ่าน"; สิทธิ์ `loan.incident_resolve` ที่ seed ไว้ **ไม่ใช่ตัวกำหนด**
- **เรื่องสิทธิ์ `loan.incident_resolve` (สำหรับผู้ดูแลสิทธิ์):** รหัสนี้ยังอยู่ในหน้ากำหนดสิทธิ์และบทบาทเดิมยังถือไว้ แต่ **ระบบไม่ได้ใช้ตัดสินแล้ว** การให้หรือถอนสิทธิ์นี้ไม่ทำให้ใครบันทึกผลได้หรือไม่ได้
  ผู้ที่บันทึกผลได้ตัดสินจากเงื่อนไขชุดเดียว (`LoanAccess::incidentResolverProblem`): บัญชีใช้งานอยู่ + ถือ **`loan.asset_approve`** + `lab_id` **ตรงสาขาของเอกสาร** + **ไม่ใช่** ผู้บันทึกเหตุ ผู้ยืม หรือผู้ทำเอกสารแทนผู้ยืม
  (ADMIN อย่างเดียวไม่ถือ `loan.asset_approve` จึงบันทึกผลไม่ได้) ถ้าต้องการให้ใครบันทึกผลได้ ให้เป็นนักวิทยาศาสตร์/ผู้ดูแลคลังของสาขานั้น ไม่ใช่ให้สิทธิ์ `loan.incident_resolve`
- **ปลดระวางของ (ขั้น 1) ทำไม่ได้ ระหว่างที่รายการนั้นยังมีของ "ไม่พร้อมใช้" หรือมีเหตุ "รอบันทึกผล"** (แก้ตาม QA 2026-11-12) ให้บันทึกผลเหตุให้ครบก่อนแล้วค่อยปลดระวาง
- ผลที่เลือกได้

  | เหตุ | ผล | ของชิ้นนั้น | ต้องมี |
  |---|---|---|---|
  | ชำรุด | ซ่อม/ตรวจแล้วใช้งานได้ | กลับเข้ากอง | หมายเหตุ ≥ 10 ตัวอักษร + สภาพหลังซ่อม (ดี/พอใช้) |
  | ชำรุด | ชดใช้แล้ว / ยกเว้น | เลือก "กลับเข้ากอง" หรือ "ตัดจำหน่าย" | เลขอ้างอิง ≥ 5 **และ** หมายเหตุ ≥ 10; กลับเข้ากองต้องมีสภาพ; ตัดจำหน่ายต้องแนบหนังสือ |
  | สูญหาย | ชดใช้แล้ว / ยกเว้น | ตัดจำหน่ายเสมอ | เลขอ้างอิง + หมายเหตุ + แนบหนังสือ |
  | ชำรุด/สูญหาย | ได้ของทดแทน | ตัดจำหน่ายของเดิม แล้วรับของใหม่เข้า | เลขอ้างอิง + หมายเหตุ + แนบหนังสือ + **ผู้รับของทดแทน** |

  ของสูญหายบันทึกเป็น "ซ่อมแล้ว" หรือ "กลับเข้ากอง" ไม่ได้ · มีเลขอ้างอิงแต่ไม่มีหมายเหตุ (หรือกลับกัน) ไม่ได้
- **ได้ของทดแทน** ต้องมีสองคน: ผู้บันทึกผลเป็น "ผู้อนุมัติ" และเลือก **ผู้รับของทดแทน** = เจ้าหน้าที่เคาน์เตอร์ของสาขา (ไม่ใช่ผู้ยืม ไม่ใช่ผู้บันทึกผลเอง; ผู้บันทึกเหตุเป็นผู้รับได้)
  ของที่ **ปลดระวางแล้ว** รับของทดแทนไม่ได้ (ตัดจำหน่ายหรือซ่อมยังบันทึกได้) — ตั้งแต่รอบแก้ตาม QA ระบบไม่ยอมให้ปลดระวางขณะมีเหตุค้าง กรณีนี้จึงเกิดได้เฉพาะข้อมูลที่ปลดระวางไว้ก่อนการแก้
- **[รอ CEO ยืนยัน] ตัดจำหน่ายจนจำนวนรวมเหลือ 0 → รายการนั้นเป็น "ปลดระวาง" อัตโนมัติ** (ไม่มีรายการเคลื่อนไหว RETIRE แยก; ของรายชิ้นที่หาย/ตัดจำหน่ายจึงปลดระวางเอง และกองที่ถูกตัดหมดจะขึ้นทะเบียนกองใหม่ได้)
- **ผลที่บันทึกแล้วแก้ไขไม่ได้** (ทั้งในระบบและที่ฐานข้อมูล: trigger `trg_loan_incidents_final`) ถ้าบันทึกผิดต้องแจ้งทีมพัฒนา ห้ามแก้ตารางด้วยมือ
- สองคนกดบันทึกผลพร้อมกัน: คนแรกสำเร็จ อีกคนได้ข้อความว่าเหตุนี้บันทึกผลไปแล้ว

**3) ไฟล์แนบของเหตุ**
- ชนิด: **รูปถ่าย** (JPG/PNG) และ **หนังสืออ้างอิง** (PDF/JPG/PNG) ไม่เกิน 10 MB ผ่านการสแกนไวรัสเหมือนไฟล์แนบอื่น **ระบบจริงต้องเปิดการสแกนไวรัส (`VIRUS_SCAN_ENABLED`) และมี ClamAV**
- แนบได้เฉพาะขณะ "รอบันทึกผล" โดยเคาน์เตอร์ของสาขาหรือผู้ที่บันทึกผลได้ · รูปถ่าย **ถ่ายเฉพาะตัวของ ห้ามติดใบหน้าหรือเอกสารส่วนบุคคล**
- **ผู้ยืมและ [รอ CEO ยืนยัน] ผู้ทำเอกสารแทนผู้ยืม เปิดหน้าเหตุและไฟล์ไม่ได้เลย** แม้เป็นเจ้าหน้าที่ของสาขาหรือ ADMIN
  (**[รอ CEO ยืนยัน]** ถ้าคนนั้นเป็นเคาน์เตอร์ที่รับคืนเอง ยัง "ส่งไฟล์เข้า" ได้จากหน้าเอกสาร แต่เปิดดูไฟล์ไม่ได้)
- การดาวน์โหลดผ่านหน้าเหตุบันทึก Audit Log ทุกครั้ง (`LOAN_INCIDENT_FILE_DOWNLOAD`)

**4) ใครเห็นอะไร (PDPA)**
- **ผู้ยืม (และผู้ทำเอกสารแทนผู้ยืม):** หน้าเอกสารเห็นเพียงว่า "มีเหตุ ประเภท จำนวน สถานะ" **ไม่เห็น** คำอธิบาย เลขอ้างอิง หมายเหตุ มูลค่า หรือไฟล์
  และในตาราง "ประวัติการเคลื่อนไหว" แถวที่เป็นของเหตุ (ชำรุด/สูญหาย/ซ่อมแล้ว/ตัดจำหน่าย/รับของทดแทน) **ไม่แสดงชื่อผู้ทำรายการ** (แก้ตาม QA 2026-11-12) คนของสาขาที่เปิดหน้าเหตุได้ยังเห็นชื่อตามเดิม
- **มูลค่าอ้างอิง ณ วันบันทึกผล** (`value_snapshot` = มูลค่าทดแทน × จำนวน) เห็นเฉพาะผู้ถือ `loan.asset_manage` (ผู้ดูแลคลังและ ADMIN) นักวิทยาศาสตร์ที่เคาน์เตอร์ไม่เห็น
- **การแจ้งเตือน** มีเฉพาะเลขเอกสารและวันที่ ไม่มีชื่อบุคคล เหตุผล เลขอ้างอิง หรือมูลค่า:
  มีเหตุรอบันทึกผล → ผู้ที่บันทึกผลได้ของสาขา (ในระบบทุกคน อีเมลเฉพาะผู้ดูแลคลัง) ·
  **มีการตัดจำหน่าย (รวม "ได้ของทดแทน") → ADMIN ทุกคน ในระบบและอีเมล** · ปรับลดจำนวน (ADJUST_OUT) ของรายการที่เคยถูกยืม → ADMIN ทุกคน

**5) ตรวจความสมบูรณ์:** `php artisan loans:verify` เพิ่มครึ่งหลังของข้อ (ค): **ยอด "ไม่พร้อมใช้" ของแต่ละรายการ = ผลรวมจำนวนของเหตุที่ยังรอบันทึกผล**
ถ้ามีการแก้ด้วยมือจะรายงาน "unavailable quantity differs from the pending incidents" และจบด้วยรหัส 1

**Audit Log ที่เกิดขึ้นในขั้น 4:** `LOAN_INCIDENT_RECORD`, `LOAN_INCIDENT_RESOLVE`, `LOAN_WRITE_OFF`, `LOAN_REPLACE_IN`, `LOAN_INCIDENT_FILE_UPLOAD`, `LOAN_INCIDENT_FILE_DOWNLOAD`
(ไม่เก็บคำอธิบายเหตุ ชื่อ หรือชื่อไฟล์ในรายละเอียด; เก็บเลขอ้างอิงภายนอกและรหัสผู้ใช้ที่เกี่ยวข้อง)

**แก้เพิ่มของขั้น 3 ที่มากับรอบนี้**
- คำขอต่อกำหนดคืน **รวมไม่เกิน 6 คำขอต่อเอกสาร นับคำขอที่ไม่อนุมัติด้วย** (`config/loans.php` `max_renewal_requests`) แยกจากเพดาน "ต่อได้ 3 ครั้ง" เดิม
- ช่องค้นหาในหน้า "ส่งมอบ/รับคืน", "ของที่ฉันยืม" และ "รายการยืมของสาขา" ถือ `%` และ `_` เป็นตัวอักษรธรรมดา (ไม่ใช่ตัวแทนอักขระ)

**ลำดับ deploy ขั้น 4 (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน หลัง CEO อนุมัติ ทำตามลำดับเท่านั้น)** — ถ้า deploy ขั้น 3-5 รวดเดียว (แนะนำ) ใช้ "ลำดับ deploy ขั้น 3–5 รวดเดียว" ด้านบนแทน

1. **สำรองฐานข้อมูลก่อนเสมอ และตรวจว่าไฟล์สำรองกู้คืนได้** — migration นี้ `ALTER` ตาราง `attachments` **ซึ่งมีข้อมูลจริงอยู่แล้ว** (เพิ่มค่า `LOAN_DOC` ต่อท้าย ENUM `doc_type`)
   แม้ไม่แก้แถวเดิม แต่เป็น DDL บนตารางที่ใช้งานอยู่: ทำช่วงที่ไม่มีผู้ใช้ และบันทึกจำนวนแถวต่อ `doc_type` ไว้เทียบหลัง migrate
2. ตรวจว่า deploy ขั้น 1-3 ครบแล้ว
3. `php artisan migrate` (ไฟล์ `2026_11_11_000002_create_loan_incidents_table.php`: สร้าง `loan_incidents` ว่างเปล่า + CHECK + trigger, เพิ่ม foreign key `fk_lm_incident` บน `loan_movements`, เพิ่ม `LOAN_DOC` ใน ENUM)
   ถ้าขั้นนี้ล้มกลางทาง **หยุด อย่ารันซ้ำ** เก็บข้อความผิดพลาดและแจ้งทีมพัฒนา (DDL ของ MariaDB ย้อนกลับเองไม่ได้)
4. **รัน `docker/mariadb/restrict_app_grants.sql` ซ้ำ ทุกฐานข้อมูล** (รวม `cmis_testing`) ไม่ต้องแก้ไฟล์สคริปต์: `loan_incidents` เป็นตารางสิทธิ์ปกติ ส่วน `loan_movements` ยังคง SELECT + INSERT เท่านั้น

5. **ไม่ต้องรัน seeder** (ขั้น 4 ไม่เพิ่มรหัสสิทธิ์) และไม่มีงานตามเวลาใหม่
6. เทียบจำนวนแถว `attachments` ต่อ `doc_type` กับที่บันทึกไว้ในข้อ 1 ต้องเท่าเดิมทุกค่า
7. ตรวจว่า **ทุกสาขามีผู้ถือ `loan.asset_approve` ที่ยังใช้งานอยู่อย่างน้อย 2 คน** (นักวิทยาศาสตร์/ผู้ดูแลคลังที่มี `lab_id` ตรงสาขา) และระบบสแกนไวรัสทำงาน
8. ทดลองหนึ่งรอบด้วยบัญชีและของทดสอบ: ยืม → ส่งมอบ → รับคืนแบบชำรุด 1 ชิ้น → อีกคนบันทึกผล "ซ่อมแล้ว" → เอกสารปิด → `php artisan loans:verify` ต้องจบด้วยรหัส 0
   (รายการเคลื่อนไหวและเหตุของการทดลองลบไม่ได้ ให้ใช้ของทดสอบที่ตั้งชื่อชัดเจน)
- **ย้อนกลับ (rollback):** `migrate:rollback` ของไฟล์นี้ **จะปฏิเสธเอง** ถ้ามีเหตุแม้รายการเดียวหรือมีไฟล์แนบชนิด `LOAN_DOC` (เพราะจะทำให้บัญชีอ้างถึงเหตุที่ไม่มี และค่า ENUM ของไฟล์หาย)
  เมื่อเริ่มใช้งานจริงแล้วทางย้อนกลับเดียวคือ **กู้คืนจากไฟล์สำรองของข้อ 1**

- ตรวจหลังติดตั้ง: `php artisan schedule:list` ต้องเห็น `loans:notify-daily` (07:00), `loans:notify-monthly` (วันที่ 1 07:30), `loans:verify --notify` (ทุกชั่วโมง)
- อีเมลแจ้งเตือนเข้าคิว (`NotificationMail` เป็นงานคิว) จึงต้องมี **queue worker** ทำงานด้วย (`iis_installation_guide.md` §8.2)
- รันมือได้ (ผู้ดูแลระบบที่มีสิทธิ์ บนเครื่องจริงหลัง CEO อนุมัติ): `php artisan loans:notify-daily` / `php artisan loans:notify-monthly --month=YYYY-MM` รันซ้ำได้ไม่ส่งซ้ำ แต่ **ไม่ควรรันทดลองบนเครื่องจริง** เพราะผู้ใช้จะได้รับข้อความจริง

**3) รายงานและ Dashboard (แท็บ "รายงาน" ในการ์ดยืม-คืน, สิทธิ์ `loan.report`)**
- เห็นได้: ผู้ดูแลคลัง (LAB_MANAGER/AUDITOR) **เฉพาะสาขาตน** และ ADMIN **ทุกสาขาหรือเลือกทีละสาขา** · ผู้ดูแลคลังที่ไม่มีสาขาเปิดได้แต่ไม่มีข้อมูล · ขอสาขาอื่นทาง URL → 403
- รายงาน 8 ตัว: ค้างคืน/เกินกำหนด · ของพร้อมให้ยืม · ประวัติเคลื่อนไหว · สรุปตามผู้ยืมและหมวดวัตถุประสงค์ (ไม่แสดงรายละเอียดที่ผู้ยืมพิมพ์เอง) · เหตุชำรุด/สูญหาย · **รายงานรายเดือนเพื่อตรวจสอบ** (ตัดจำหน่าย ปรับยอด รับของทดแทน พร้อมข้อสังเกตเมื่อเลขอ้างอิงขาด/สั้น/ซ้ำ) · รายการที่ผู้ยืมทำกับเอกสารตนเอง (`LOAN_SELF_*`) · ตัวชี้วัด
- **ราคา/มูลค่า** แสดงเฉพาะผู้ถือ `loan.asset_manage` · รายงานเหตุไม่แสดงคำอธิบายเหตุ/หมายเหตุ และไม่แสดงเหตุของเอกสารที่ผู้ดูเป็นผู้ยืมหรือผู้ทำแทน
- **รายงานประวัติเคลื่อนไหว และรายงานรายเดือนเพื่อตรวจสอบ:** แถวที่เป็นของเหตุในเอกสารที่ **ผู้ดูรายงานเป็นผู้ยืมหรือผู้ทำแทนเอง** ยังแสดงแถว (อะไร เมื่อไร กี่ชิ้น เลขเอกสาร)
  แต่ช่องผู้ทำรายการ ผู้อนุมัติ เลขอ้างอิงภายนอก (และในรายงานรายเดือน: หนังสือแนบ ข้อสังเกต) แสดงเป็น "(ซ่อน: เหตุของเอกสารที่คุณเป็นผู้ยืม/ผู้ทำคำขอแทน)" ให้ผู้ดูแลคลัง/ADMIN อีกคนเป็นผู้ตรวจแถวเหล่านั้น
- **ตัวชี้วัด "คืนช้า"** นับเอกสารที่ปิดแล้วซึ่ง **ของชิ้นสุดท้ายกลับมา (คืนปกติ/คืนชำรุด/บันทึกสูญหาย) หลังวันครบกำหนด** ไม่ได้นับจากวันปิดเอกสาร (วันปิดคือวันที่บันทึกผลเหตุรายการสุดท้าย ซึ่งไม่ใช่ความล่าช้าของผู้ยืม) แก้ตาม QA 2026-11-12
- **ส่งออก CSV ทุกครั้งลง Audit Log `LOAN_REPORT_EXPORT`** (ใคร รายงานใด สาขาใด ตัวกรองใด กี่แถว) **ไม่เก็บคำที่พิมพ์ค้น** (เก็บเพียงว่ามีการค้น) ทุกช่องผ่านตัวกัน CSV injection (ขึ้นต้น `= + - @` ใส่ `'` นำหน้า)
  ไฟล์มีชื่อบุคคล ผู้ส่งออกต้องเก็บรักษาตาม PDPA

**4) นำเข้าทะเบียนของให้ยืมจากไฟล์ CSV (ครั้งแรกของแต่ละสาขา)**

```
php artisan loans:import-assets <ไฟล์.csv> --lab=<รหัสสาขา> --by=<username> --dry-run   # ตรวจก่อนเสมอ ไม่บันทึกอะไร
php artisan loans:import-assets <ไฟล์.csv> --lab=<รหัสสาขา> --by=<username>             # นำเข้าจริง
```
- ไฟล์ UTF-8 (มี BOM ได้) บรรทัดแรกเป็นชื่อคอลัมน์: `item_code`, `tracking_mode` (UNIT/POOL), `qty` (จำเป็น 3 ช่องนี้), `asset_tag` (**แถว UNIT ต้องมีเสมอ** แถว POOL ห้ามมี), `location_code` (ของสาขานั้น), `max_loan_days` (1-365), `replacement_value` (ทศนิยมไม่เกิน 2), `condition_note` (≤ 255)
- สูงสุด **2,000 แถว** ต่อไฟล์ · ไฟล์มีปัญหาแม้แถวเดียว **ไม่บันทึกเลยทั้งไฟล์** (แสดงบรรทัดและปัญหา) · ไฟล์ถูกต้องบันทึกทั้งหมดใน transaction เดียว ทุกแถวเป็นการขึ้นทะเบียนปกติ (REGISTER + hash chain + `LOAN_ASSET_REGISTER`) และมี `LOAN_ASSET_IMPORT` หนึ่งแถว (สาขา จำนวนแถว sha256 ของไฟล์)
- `--by` ต้องเป็นผู้ใช้ที่ใช้งานอยู่ ถือ `loan.asset_manage` ของสาขานั้น หรือเป็น ADMIN · สาขาต้องเปิดใช้งาน
- **`--by` ต้องได้ความยินยอมจากเจ้าของบัญชีนั้นก่อนทุกครั้ง** ทุกแถวที่นำเข้าจะถูกบันทึกในบัญชีคุมและ Audit Log ว่า **เจ้าของบัญชีนั้นเป็นผู้ขึ้นทะเบียน** (ไม่ใช่ผู้ที่พิมพ์คำสั่ง)
  ให้ใช้ชื่อบัญชีของผู้ดูแลคลังที่ตรวจไฟล์และรับผิดชอบรายการนั้นจริง เก็บหลักฐานความยินยอม (เช่น บันทึกข้อความ/อีเมล) ไว้คู่กับไฟล์ ห้ามใช้ชื่อบัญชีของคนอื่นโดยเจ้าของไม่รู้
- **แถว UNIT ที่ไม่มี `asset_tag` ถูกปฏิเสธ (ทั้งไฟล์ไม่บันทึก)** การนำเข้าไม่สร้างเลขให้อัตโนมัติ (แก้ตาม QA 2026-11-12) จึง **รันไฟล์เดิมซ้ำถูกปฏิเสธทั้งไฟล์เสมอ** (เลขประจำตัวของ/กอง POOL มีในทะเบียนแล้ว) ไม่เกิดของซ้ำ
  การขึ้นทะเบียนทีละชิ้นทางหน้าเว็บยังเว้นเลขไว้ให้ระบบสร้างได้ตามเดิม
- หลังนำเข้า รัน `php artisan loans:verify` ต้องจบด้วยรหัส 0 · แถวที่นำเข้าแล้วลบไม่ได้ (ปลดระวางได้ตามขั้น 1)

### คลัง IMS → คลังใช้งาน, แก้รายละเอียดวัสดุ และประเภทวัสดุ 3 ค่า (ITM-2610-062 ปรับตามผู้ดูแลคลัง 2026-11-05 และ ITM-2610-063) [ร่าง รอ CEO ตรวจ — ชุดเต็ม 1,625 ผ่าน, pint/phpstan สะอาด (2026-11-05)]

ใบเบิกของมหาวิทยาลัยเป็นกระดาษ ผู้ดูแลคลังย้ายของจาก IMS (คลังกลางสาขา) เข้า **คลังใช้งาน** แล้วคนเบิกจึงเบิกได้ (CEO ตัดสิน 2026-11-05)
หลังคุยกับผู้ดูแลคลัง CEO สั่ง **เอาหน้า "ย้ายตามใบเบิกกระดาษ" (หน้าย้ายหลายรายการ) ออก** เหลือวิธีย้ายทีละ Lot วิธีเดียว

**หลักการ (คงเดิม)**
- ผู้ใช้ทุกคน **ดู** ของใน IMS ได้ (`ims.browse` คงเดิม) แต่ **เบิก/จ่ายได้จากคลังใช้งานเท่านั้น**
- ตอนจ่าย ถ้าคลังใช้งานไม่พอ ระบบ **ปฏิเสธทั้งแถว** และ **ไม่ตัดจาก IMS ให้อัตโนมัติ** แถวที่ถูกปฏิเสธไม่ทำให้ใบเบิกเปลี่ยนสถานะ
  (ยัง APPROVED / PARTIALLY_ISSUED ตามเดิม) และไม่กระทบแถวอื่นของใบเดียวกัน
- ตัวเลข "คงเหลือ" ของร้านและหน้าจ่าย **ไม่รวมคลังกลาง (IMS)** (หน้าจ่ายแสดงยอด IMS แยกไว้ให้ดูเท่านั้น)

**ย้ายจาก IMS เข้าคลังใช้งาน ทีละ Lot (วิธีเดียวที่เหลือ)**
1. เมนูงานคลัง → แท็บ "IMS" (รายการ Lot) ค้นรหัส/ชื่อ/เลข Lot แล้วกด **"ย้ายเข้าคลังใช้งาน"** ที่แถวของ Lot นั้น (ปุ่มขึ้นเฉพาะผู้ที่มีสิทธิ์ย้าย Lot นั้น)
2. กรอกเลขที่ใบเบิก/แหล่งที่มา เลือกรูปแบบการติดตาม (แยกเป็นขวดมีบาร์โค้ดทุกขวด หรือรวมเป็นก้อนเดียว) ปริมาณและหน่วย และ **ที่จัดเก็บ** (ต้องเป็นที่เก็บของสาขาเดียวกับ Lot) แล้วยืนยัน
3. ระบบตัดยอด Lot, สร้างภาชนะ (พร้อมบาร์โค้ดให้พิมพ์ฉลาก), เขียนแถว "รับเข้า" ในบัญชีคุม และเขียน `ims_movements` ประเภท ISSUE ในทรานแซกชันเดียว
- **ใครย้ายได้:** ผู้ถือ `ims.manage` (LAB_MANAGER / AUDITOR) ที่ผูกสาขาเดียวกับ Lot **และถือชนิดของ Lot นั้น** (หน้า "ผู้ใช้งานและสิทธิ์") ผู้ที่ไม่ถือชนิดนั้นได้ 403
  ADMIN และนักวิทยาศาสตร์ย้ายไม่ได้ · **Lot ของวัสดุวิทยาศาสตร์ (ยืม-คืน) ไม่มีปุ่มย้ายและถูกปฏิเสธ (403) ทุกคน** เพราะของยืม-คืนไม่ถูกตัดเข้าคลังใช้งาน (การย้าย IMS → ทะเบียนยืม CEO เลื่อนไปขั้นหลัง)
- ย้ายทีละ Lot รับเศษแพ็กได้ ย้ายผิดไม่มีขั้นย้อนกลับ สมุดสต็อกเป็น append-only ต้องแก้ด้วย **ปรับยอด (ADJUST)** ในเมนูปรับยอด (ต้องมีผู้อนุมัติอีกคนตามกฎเดิม)
- ที่เก็บปลายทางยังไม่แยกตามคลังสารเคมี/วัสดุ (รอ CEO ตัดสิน) จึงควรตรวจที่เก็บให้ตรงชนิดเอง
- **ที่ถูกถอดออก (ไม่ต้องใช้แล้ว):** เมนู/หน้า "ย้ายตามใบเบิกกระดาษ", เลขที่ใบกระดาษแบบหลายแถวและการเตือนเลขซ้ำ, Audit Log `IMS_TRANSFER_BATCH`
  (รายการเก่าใน Audit Log ยังอยู่ ลบไม่ได้) การย้ายทีละ Lot เขียนบันทึกตามปกติของมันเอง

**ปุ่ม "ขอให้เติมคลังใช้งาน" (ร้านค้า) — คงเดิม**
- ของที่มีแต่ใน IMS จะขึ้นบนชั้นพร้อมป้าย "มีในคลังกลาง ยังเบิกไม่ได้" ไม่มีปุ่มใส่ตะกร้า แต่มีปุ่ม "ขอให้เติมคลังใช้งาน"
- กดแล้วระบบ **แจ้งในระบบ (ไม่ส่งอีเมล)** ถึงผู้ใช้ที่ active ในสาขาเดียวกันที่ถือชนิดนั้น (ADMIN ล้วนไม่ถูกนับ) **ลิงก์ในการแจ้งเตือนพาไปหน้ารายการ Lot ของ IMS ที่ค้นด้วยรหัสวัสดุนั้น** (`ims.lots.index?search=<รหัส>`) เพื่อให้ผู้ดูแลกดย้ายทีละ Lot
- ถ้าสาขานั้นไม่มีผู้ถือชนิดนี้ ผู้กดเห็นข้อความ "ยังไม่มีผู้ดูแลคลังชนิดนี้ในสาขา" (ไม่นับโควตา) → ADMIN ควรกำหนดชนิดให้ผู้ดูแล
- จำกัดการกดรัว: สินค้าเดิมกดได้ 1 ครั้ง/วัน/คน และรวมไม่เกิน 20 ครั้ง/วัน/คน · ทุกครั้งบันทึก Audit Log `SHOP_REFILL_REQUEST` (ไม่มีตารางเก็บคำขอ)
- **วัสดุวิทยาศาสตร์ (ยืม-คืน) ไม่มีปุ่มนี้** (ไม่ขึ้นร้านเลย)

**หน้าจ่าย:** ถ้าแถวใดคลังใช้งานไม่พอ จะมีกล่อง "ของไม่พอในคลังใช้งาน" บอกยอดที่ต้องจ่าย/คลังใช้งานมี/คลังกลางมี
และมีปุ่ม **"ไปหน้า Lot เพื่อย้ายเข้าคลังใช้งาน"** ที่ลิงก์ไปรายการ Lot ของ IMS ที่ค้นด้วยรหัสวัสดุนั้น (แสดง **เฉพาะผู้ที่มีสิทธิ์ย้ายชนิดนั้น**)

**ประเภทวัสดุ 3 ค่า (ITM-2610-063, CEO 2026-11-05)**
- ประเภทของวัสดุไม่ได้เก็บเป็นคอลัมน์ แต่ **มาจากหมวดหมู่ (`item_categories`)** ของวัสดุนั้น: **สารเคมี** (หมวดที่ติ๊กเป็นสารเคมี) · **วัสดุสิ้นเปลือง** (หมวดอื่นที่ไม่ใช่สารเคมี)
  · **วัสดุวิทยาศาสตร์ (ยืม-คืน)** (หมวดพิเศษรหัส `LOAN_SCIENCE` ชื่อ "วัสดุวิทยาศาสตร์ (ยืม-คืน)") เปลี่ยนประเภทของวัสดุ = เปลี่ยนหมวดหมู่ของวัสดุนั้น
- **วัสดุวิทยาศาสตร์ (ยืม-คืน) เบิกไม่ได้:** ไม่ขึ้นในร้าน หน้าสินค้าเปิดไม่ได้ (404) ใส่ตะกร้า/สั่งเบิก/ขอเติมไม่ได้ ไม่ขึ้นในช่องค้นสินค้าของใบเบิก
  เพิ่มลงใบเบิกไม่ได้ และจ่ายตามใบเบิกไม่ได้ (ตรวจฝั่งเซิร์ฟเวอร์ ไม่ใช่แค่ซ่อน) ใช้ระบบ "ยืม-คืนวัสดุ" แทน
- **ผู้ดูแลชนิดวัสดุวิทยาศาสตร์ ต้องให้ ADMIN ติ๊กให้เอง:** หน้า "ผู้ใช้งานและสิทธิ์" ใต้ชื่อผู้ดูแลมีปุ่มที่ 3 "วัสดุวิทยาศาสตร์ (ยืม-คืน)" (บันทึก Audit Log `ITEM_TYPE_CHANGE` เหมือนเดิม)
  **คำสั่ง `managers:backfill-item-types` ให้เฉพาะ 2 ชนิดเดิม (สารเคมี/วัสดุสิ้นเปลือง) ไม่ให้ชนิดนี้อัตโนมัติ** และไม่ตัดสิทธิ์ผู้ที่มีแถวอยู่แล้ว
  ADMIN ถือครบทั้ง 3 ชนิดโดยอัตโนมัติ (แต่ยังเขียนบัญชีคุม/แก้ผ่านหน้า IMS ไม่ได้ตามเดิม)
- **ใบเบิกเก่าที่ค้างอยู่:** ใบที่ยังไม่สิ้นสุดและมีรายการวัสดุที่ถูกย้ายเป็นวัสดุวิทยาศาสตร์ภายหลัง จะจ่ายไม่ได้ (ระบบแจ้งว่าเบิกไม่ได้) ส่วนใบที่สิ้นสุดแล้ว (ISSUED/REJECTED/CANCELLED)
  ยังเปิดดู/พิมพ์/รายงานได้ตามเดิม และนับเป็นชนิด "วัสดุวิทยาศาสตร์" ในรายงานตรวจก่อนเปลี่ยนระบบ
- **ใบเบิกค้างกันการเปลี่ยนประเภท:** เปลี่ยนวัสดุ **เป็น** หรือ **จาก** วัสดุวิทยาศาสตร์ไม่ได้ ถ้ามีใบเบิกที่ยังไม่สิ้นสุด (สถานะอื่นนอกจาก ISSUED/REJECTED/CANCELLED **รวมใบร่าง DRAFT**)
  อ้างวัสดุนั้นอยู่ ระบบแจ้งเลขที่ใบ (แสดงสูงสุด 5 ใบ) ที่ช่องหมวดหมู่ ให้รอใบเหล่านั้นสิ้นสุดก่อน · เปลี่ยนระหว่างสารเคมี ↔ วัสดุสิ้นเปลืองไม่ถูกกัน

**ข้อสังเกต (รอ CEO ตัดสิน)**
- ใบเบิกที่จบแล้วจะถูกตีความชนิดตาม **หมวดปัจจุบัน** ของวัสดุ: ถ้าวัสดุถูกย้ายชนิดภายหลัง ผู้ดูแลชนิดเดิมอาจไม่เห็นใบเก่านั้นในรายการของตน
- ทะเบียนวัสดุ (`item.manage`) **ไม่จำกัดตามชนิด/สาขา** ต่างจากหน้า IMS ที่จำกัดตามสาขาและชนิดที่ถือ
- ADMIN ไม่มี `item.manage` / `ims.manage` จึงแก้รายละเอียดวัสดุไม่ได้ (ดูหัวข้อสิทธิ์ด้านล่าง)

**แก้รายละเอียดวัสดุได้ 2 ที่ (ข้อมูลชุดเดียวกัน)**
- **ที่ทะเบียนวัสดุ** (เมนูทะเบียนวัสดุ → แก้ไข) แก้ได้ทุกฟิลด์ · **ที่หน้า Lot ของ IMS** ปุ่ม **"แก้รายละเอียดวัสดุ"** (ที่รายการ Lot และหน้ารายละเอียด Lot) แก้ได้ 10 ฟิลด์:
  หมวดหมู่ (= ประเภท), ชื่อไทย, ชื่ออังกฤษ, เลข CAS, สูตร, ยี่ห้อ, เกรด, สถานะทางกายภาพ, สเปก, ประเภทการจัดเก็บ
  ฟิลด์อื่น (รหัสรายการ หน่วยฐาน ขนาดบรรจุ ความหนาแน่น จุดสั่งซื้อ สารควบคุม GHS ฯลฯ) **แก้ได้เฉพาะที่ทะเบียนวัสดุ** หน้า IMS แสดงอ่านอย่างเดียว และแม้ส่งมาตรง ๆ ก็ไม่ถูกบันทึก
- **สิทธิ์แก้จากหน้า IMS:** ต้องมี `ims.manage` + เป็นของสาขาเดียวกับ Lot + **ถือชนิดเดิมของวัสดุนั้น** · ถ้าจะเปลี่ยนไปประเภทอื่น ต้อง **ถือประเภทใหม่ด้วย** (ไม่ถือ → ข้อความที่ช่องหมวดหมู่ "คุณไม่ได้ดูแลวัสดุประเภทที่เลือก…")
  ผู้ไม่มีสิทธิ์ได้ 403 · **ADMIN ไม่มี `ims.manage` จึงเปิดหน้าแก้จาก IMS ไม่ได้ (403)** และ ณ ปัจจุบัน ADMIN ก็ไม่มี `item.manage` จึงแก้ที่ทะเบียนวัสดุ (`items.update`) ไม่ได้เช่นกัน
  (มีเฉพาะ LAB_MANAGER/AUDITOR; เทสต์ยืนยันแล้ว) — **รอ CEO ยืนยันว่าต้องการให้ ADMIN แก้รายละเอียดวัสดุได้หรือไม่** (ถ้าต้องการ ต้องเพิ่มสิทธิ์ผ่านทีมพัฒนา)
- **Audit Log:** ทุกการแก้บันทึก `ITEM_UPDATE` 1 แถว: ใคร, แหล่ง (`items.update` = ทะเบียนวัสดุ หรือ `ims.lot` = หน้า IMS พร้อมรหัส Lot), ค่าก่อน/หลัง **เฉพาะฟิลด์ที่เปลี่ยนจริง** ถ้าบันทึกโดยไม่มีอะไรเปลี่ยนจะไม่เขียน

**คำสั่งตรวจก่อนเปลี่ยนระบบ (อ่านอย่างเดียว ไม่แก้ยอด):** `php artisan ims:reconcile-working-stock [--lab=รหัสหรือ id สาขา]`
1. เทียบรายรหัสสินค้า: ยอดคงเหลือใน IMS กับยอดภาชนะคงเหลือในคลังใช้งาน (นับเฉพาะที่เก็บที่ผูกสาขา สถานะ SEALED/IN_USE) แถวที่ "มีทั้งสองที่" ให้ตรวจนับซ้ำ · **วัสดุวิทยาศาสตร์ (ยืม-คืน) ถูกข้าม**
2. ภาชนะที่ไม่มีที่เก็บ / ที่เก็บไม่ผูกสาขา / คนละสาขากับ Lot ต้นทาง (ภาชนะเหล่านี้ **ไม่นับเป็นของที่เบิกได้** ต้องแก้ที่เก็บก่อน)
3. ใบเบิกที่อนุมัติ/จ่ายบางส่วนค้างอยู่ ซึ่งแถวนั้นคลังใช้งานไม่พอแต่ IMS มี (นับต่อสาขาและชนิด; ใบค้างที่มีรายการวัสดุวิทยาศาสตร์ ขึ้นเป็นแถวแยก "วัสดุวิทยาศาสตร์") ต้องให้ผู้ดูแลย้ายเข้าคลังใช้งานก่อนจ่าย
4. ผู้ดูแลหลักของแต่ละชนิดต่อสาขา (0 คนหรือมากกว่า 1 คน = เตือนเท่านั้น ไม่บังคับ)
ผู้ดูแลตัดสินใจรายตัวและแก้ผ่านเมนูปรับยอดเดิม คำสั่งนี้ไม่แก้ข้อมูลใด ๆ

**ลำดับ deploy (ผู้ดูแลระบบที่มีสิทธิ์เป็นผู้รัน หลัง CEO อนุมัติ ทำตามลำดับ)**
0. ก่อนเริ่ม: ต้องรัน `managers:backfill-item-types` แล้ว (ผู้ดูแลทุกคนมีแถวชนิด) และผู้ใช้ทุกคนมี `lab_id`
1. สำรองฐานข้อมูล
2. pull / build — **ไม่มี migration ใหม่ ไม่ต้องรัน PermissionSeeder** (ไม่มีสิทธิ์ใหม่ ไม่มีตารางใหม่ ไม่ต้องแก้ grants) แล้วรัน `php artisan view:clear` (หน้า "ย้ายตามใบเบิกกระดาษ" ที่ถูกลบมี compiled view ค้างอยู่)
   * **ไม่มีหน้าย้ายตามใบกระดาษแล้ว** การย้ายจาก IMS ใช้ย้ายทีละล็อตเท่านั้น
   * โค้ดชุดนี้ถอดการตัด IMS อัตโนมัติออกแล้ว (ตั้งแต่ ITM-2610-062): นับจากนาทีนี้ใบเบิกที่ค้างและเคยพึ่งการตัดอัตโนมัติจะ **จ่ายไม่ได้** จนกว่าจะย้ายของ (ปลอดภัย ไม่ทำให้ยอดเพี้ยน) ควรทำนอกเวลาทำงาน
3. **เพิ่มหมวดวัสดุวิทยาศาสตร์:** รัน `php artisan db:seed --class=ItemCategorySeeder --force` (รันซ้ำได้ ไม่ซ้ำแถว ไม่แตะหมวดเดิม ตรวจได้ว่ามีหมวดรหัส `LOAN_SCIENCE` เพิ่มมา 1 แถวและหมวดอื่นเท่าเดิม)
   ถ้าไม่รัน หมวด "วัสดุวิทยาศาสตร์ (ยืม-คืน)" จะไม่มีให้เลือก (ส่วนอื่นของระบบไม่พัง)
4. รีสตาร์ต queue worker (ปุ่มขอเติมแจ้งในระบบ)
5. ให้ ADMIN ติ๊กชนิด "วัสดุวิทยาศาสตร์ (ยืม-คืน)" ให้ผู้ดูแลที่รับผิดชอบ (ระบบไม่ให้เอง)
6. รัน `php artisan ims:reconcile-working-stock` ทุกสาขา (อ่านอย่างเดียว) ส่งรายงานให้ผู้ดูแลคลังแต่ละชนิด ผู้ดูแลย้ายของค้างทีละ Lot (หน้ารายการ Lot ของ IMS) และแก้ภาชนะที่ที่เก็บผิดปกติ แล้วรันรายงานซ้ำจนส่วน 2 และ 3 ว่าง
7. ตรวจชั้นวางร้านและทำ UAT (docs/uat_test_plan.md ส่วน 2.8 และ 2.9)

## 3. Audit Log

ทุกการกระทำสำคัญในระบบ (ล็อกอิน, สร้าง/แก้ไข/อนุมัติ/ปฏิเสธ ทุกประเภทเอกสาร) ถูกบันทึกไว้ใน Audit Log
โดยอัตโนมัติ **แก้ไขหรือลบไม่ได้แม้แต่ ADMIN เอง** (append-only เหมือนบัญชีคุมวัสดุ) เข้าถึงได้ผ่านสิทธิ์
`audit.view` — ปัจจุบันยังไม่มีหน้าจอค้นหา/กรอง Audit Log โดยเฉพาะ (ต้องดูผ่านฐานข้อมูลโดยตรงหรือรอ UI
เพิ่มเติมในอนาคต) — บันทึกไว้เป็นข้อจำกัดที่ทราบอยู่แล้ว

## 4. การตรวจสอบความสมบูรณ์ของบัญชีคุม (Hash Chain)

บัญชีคุมวัสดุทุกแถวเชื่อมโยงกันด้วย hash chain (คล้ายหลักการของ blockchain แบบง่าย) เพื่อรับประกันว่าไม่มี
ใครแก้ไขประวัติย้อนหลังได้โดยไม่ถูกตรวจจับ

- **ตรวจสอบด้วยตนเอง**: รันคำสั่ง `php artisan ledger:verify` (ผ่าน SSH/RDP เข้าเซิร์ฟเวอร์ หรือให้ผู้ดูแล
  ระบบเทคนิครันให้) จะรายงานว่า chain สมบูรณ์ 100% หรือพบจุดที่ขาดหาย/ถูกแก้ไข
- **ตรวจสอบอัตโนมัติ**: ระบบตรวจสอบให้เองทุกชั่วโมง ถ้าพบความผิดปกติจะ**ส่งอีเมลแจ้งเตือน ADMIN ทุกคน
  ทันที** (ไม่มีการแจ้งเตือนในระบบ เฉพาะอีเมลเท่านั้น เนื่องจากเป็นเหตุการณ์ร้ายแรงที่ควรรู้แม้ไม่ได้
  เปิดระบบอยู่)

ถ้าพบว่า chain ไม่สมบูรณ์ **ควรถือเป็นเหตุการณ์ด้านความปลอดภัยข้อมูล (security incident)** — ดูขั้นตอน
รับมือใน `pdpa_breach_response_plan.md` ประกอบ (แม้ชื่อไฟล์จะเน้น PDPA แต่ขั้นตอนแจ้งเหตุ/ทีมรับผิดชอบใช้
ร่วมกันได้กับเหตุการณ์ด้านความปลอดภัยข้อมูลทุกประเภท)

## 6. PDPA — สิทธิ์ของเจ้าของข้อมูลและหน้าที่ผู้ดูแลระบบ

- ผู้ใช้ทุกคนมีสิทธิ์ดู/ขอสำเนาข้อมูลส่วนตัวของตนเองผ่านเมนู "ข้อมูลของฉัน" ด้วยตนเอง (ไม่ต้องผ่าน ADMIN)
- **การลบ/ปกปิดข้อมูลผู้ใช้ที่พ้นสภาพ**: รันคำสั่ง `php artisan users:pseudonymize {user}` (ระบุ ID หรือ
  username ของผู้ใช้ที่ต้องการ) — ระบบจะเขียนทับชื่อ-นามสกุล, username, อีเมล, เบอร์โทร, รหัสนิสิต/พนักงาน
  ด้วยค่าที่ไม่สามารถระบุตัวตนได้ แต่**คงประวัติการทำธุรกรรม (ใบเบิก, บัญชีคุม) ไว้ครบ** เพื่อรักษาความ
  ถูกต้องของบัญชีคุมวัสดุ (ห้ามลบแถวใน ledger ไม่ว่ากรณีใด) — คำสั่งนี้มีการถามยืนยันก่อนทำงานเสมอ (ป้องกัน
  การรันผิดพลาด) และ**ไม่มีการรันอัตโนมัติตามกำหนดเวลา** (ต้องรอนโยบายระยะเวลาการเก็บรักษาข้อมูลที่ชัดเจน
  จากมหาวิทยาลัย/คณะก่อน — ดู `pdpa_breach_response_plan.md` และ CLAUDE.md's Known open items)
- ถ้าเกิดเหตุข้อมูลรั่วไหล ให้ปฏิบัติตามขั้นตอนใน `pdpa_breach_response_plan.md` ทันที (มีกำหนดแจ้ง
  สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ภายใน 72 ชั่วโมงตามกฎหมาย)

## 7. การสำรองและกู้คืนข้อมูล

ดูรายละเอียดฉบับเต็มที่ `docs/backup_restore_runbook.md` — สรุปสิ่งที่ ADMIN ควรรู้:

- ระบบสำรองข้อมูลแบบเต็มทุกวัน + บันทึกการเปลี่ยนแปลงต่อเนื่อง (binlog) ทำให้กู้คืนย้อนไปยังจุดเวลาใดก็ได้
  ระหว่างการสำรองสองครั้งล่าสุด (RPO ≤ 15 นาที)
- **ทดสอบการกู้คืนเป็นระยะ** (drill) เพื่อยืนยันว่ากลไกยังทำงานถูกต้อง — มีสคริปต์อัตโนมัติที่กู้คืนลง
  ฐานข้อมูลแยกต่างหาก **ไม่กระทบข้อมูลจริงเลย** ใช้ทดสอบได้บ่อยเท่าที่ต้องการ
- ถ้าเกิดเหตุต้องกู้คืนจริง เป็นงานของทีมเทคนิค/ผู้ดูแลระบบฐานข้อมูลโดยตรง ไม่ใช่งานที่ทำผ่านหน้าเว็บ CMIS

## 8. สำหรับผู้ตรวจสอบ (AUDITOR)

บทบาท AUDITOR ถูกปรับบทบาทเมื่อ 2026-09-21 (ตามคำสั่ง CEO): **ไม่ใช่บทบาทอ่านอย่างเดียวแล้ว** แต่เป็นผู้ดูแลคลัง
ประจำสาขา (ชื่อแสดง "ผู้ดูแลคลัง") ที่ถืออยู่ในสิทธิ์**เท่ากับ LAB_MANAGER ทุกประการ** (กำหนดแยกต่อผู้ใช้ได้):

- ดูใบขอเบิกทั้งหมด, พิจารณาใบขอเบิก, **จ่าย/รับคืนของตามใบเบิก (สาขาและชนิดที่รับผิดชอบ)**, อนุมัติจ่ายเกิน 10%
- รับของเข้าคลัง, ตรวจนับสต๊อก, ขอทำลายและอนุมัติทำลาย/ตัดจำหน่าย, อนุมัติปรับปรุงยอด, ดูบัญชีคุม
- จัดการทะเบียนสารเคมี/ผังจัดเก็บ/สมาชิกที่เบิกได้, จัดการคลัง IMS, ดูรายงาน
- **ไม่มี**: ตรวจสอบ Hash Chain (`ledger.verify`) และ Audit Log (`audit.view`) — ถอนออกจาก AUDITOR แล้ว (LAB_MANAGER ก็ไม่มี) ปัจจุบันเป็นของ ADMIN เท่านั้น
- ขอบเขตการทำงานจำกัดตามสาขาของผู้ใช้ (ดู `User::isBranchManager()`)

## 9. การบูตสแตรปบัญชีผู้ดูแลระบบคนแรก

ระบบใหม่ (หรือฐานข้อมูลที่เพิ่งกู้คืน/ติดตั้งใหม่) จะ**ไม่มี ADMIN คนใดเลย** — เป็นสถานการณ์ไก่กับไข่ที่ต้อง
แก้ด้วยมือครั้งเดียว:

1. ให้ผู้ที่จะเป็น ADMIN คนแรกล็อกอินผ่านระบบตามปกติ (ข้อ 1 ของคู่มือผู้ใช้) — จะไปค้างที่หน้า "รอผู้ดูแล
   ระบบกำหนดสิทธิ์การใช้งาน" เป็นธรรมดา เพราะยังไม่มีใครมอบสิทธิ์ให้ได้เลยตอนนี้
2. ให้ผู้ดูแลระบบเทคนิค (ผู้มีสิทธิ์เข้าเซิร์ฟเวอร์โดยตรง) รันคำสั่งนี้ผ่าน `php artisan tinker`:
   ```php
   $user = App\Models\User::where('username', '<username ของคนที่ล็อกอินไว้>')->firstOrFail();
   $user->roles()->attach(App\Models\Role::where('code', 'ADMIN')->firstOrFail());
   ```
3. ให้ผู้ใช้คนนั้นรีเฟรชหน้าเว็บ (หรือล็อกอินใหม่) — จะเห็นเมนู "ผู้ใช้งานและสิทธิ์" ปรากฏขึ้น และสามารถ
   มอบสิทธิ์ให้ผู้ใช้คนอื่น ๆ ต่อผ่านหน้าเว็บได้ตามปกติ (ข้อ 1) **ไม่ต้องใช้วิธีนี้ซ้ำอีก**
