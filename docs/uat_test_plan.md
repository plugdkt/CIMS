# แผนทดสอบการยอมรับของผู้ใช้ (UAT Test Plan) — CMIS

เอกสารนี้เป็นชุดสถานการณ์ทดสอบสำหรับให้ **ผู้ใช้จริง** (ตัวแทนแต่ละบทบาท) ทดสอบระบบก่อนเปิดใช้งานจริง —
ไม่ใช่เทสต์อัตโนมัติ (ดูชุดทดสอบอัตโนมัติ 367 รายการที่ `tests/Feature` และ `tests/Unit` สำหรับการตรวจสอบ
เชิงเทคนิค) แต่เป็นการยืนยันว่า **ผู้ใช้จริงใช้งานได้จริงตามที่คาดหวัง** ในสภาพแวดล้อมจริง

> **หมายเหตุสำคัญ**: เอกสารนี้เตรียมสถานการณ์ทดสอบและเกณฑ์ผ่าน/ไม่ผ่านไว้ให้ — **แต่การทดสอบจริงต้องทำโดย
> มนุษย์ (ตัวแทนผู้ใช้แต่ละบทบาท) ไม่ใช่ระบบอัตโนมัติ** เนื่องจาก UAT วัดประสบการณ์การใช้งานจริง ความเข้าใจ
> ของผู้ใช้ และความสอดคล้องกับกระบวนการทำงานจริงของหน่วยงาน ซึ่งเป็นสิ่งที่ automate ไม่ได้โดยธรรมชาติ

## วิธีใช้เอกสารนี้

1. เตรียมบัญชีทดสอบ 1 บัญชีต่อบทบาท (STUDENT, ADVISOR, SCIENTIST, LAB_MANAGER, ADMIN, AUDITOR) — ควรเป็น
   บัญชี MEDSCI ACC จริงที่ ADMIN กำหนดบทบาทให้ทาง `/admin/users` ไม่ใช่บัญชีทดสอบที่สร้างผ่าน tinker
2. ให้ผู้ทดสอบแต่ละคนทำตามสถานการณ์ที่ตรงกับบทบาทตนเอง เรียงตามลำดับ (บาง scenario ต้องรอผลจากอีกบทบาท
   หนึ่งก่อน เช่น สถานการณ์ที่ 3 ต้องรอสถานการณ์ที่ 2 อนุมัติก่อน)
3. บันทึกผลแต่ละข้อ: ✅ ผ่าน / ❌ ไม่ผ่าน (พร้อมรายละเอียด) / ⚠️ ผ่านแต่มีข้อสังเกต
4. รวบรวมผลทั้งหมดก่อนตัดสินใจ Go-Live

## ส่วนที่ 1: สถานการณ์ทดสอบตามเกณฑ์การยอมรับ (spec §14)

| # | สถานการณ์ | ขั้นตอน | เกณฑ์ผ่าน |
|---|---|---|---|
| 1 | นิสิตส่งใบเบิกโดยยังไม่ได้รับอนุมัติจากอาจารย์ที่ปรึกษา | นิสิตสร้างใบเบิก → ส่ง → **ยังไม่ให้อาจารย์อนุมัติ** → ให้นักวิทยาศาสตร์ลองเปิดหน้าจ่ายของ | นักวิทยาศาสตร์ต้องกดจ่ายของไม่ได้ (ปุ่มไม่ปรากฏ หรือระบบปฏิเสธ) |
| 2 | เบิกสารเคมีบางส่วนจากขวดใหญ่ | รับเข้าขวดสารเคมี 500 g เข้าคลัง → นิสิต/เจ้าหน้าที่เบิก 12.5 g → นักวิทยาศาสตร์จ่ายของ | ยอดคงเหลือในบัญชีคุมต้องแสดง 487.5 g พอดี (ไม่ปัดเศษผิด) |
| 3 | เบิกซ้ำหลายครั้งจนเกือบหมดขวด | รับเข้าขวด 1 g → เบิก-จ่าย 0.001 g ติดต่อกัน 1,000 ครั้ง (ผู้ทดสอบเทคนิคอาจช่วยเขียนสคริปต์ช่วยยิงซ้ำแทนการคลิกมือ 1,000 ครั้ง) | ยอดคงเหลือสุดท้ายต้องเป็น 0.000000 พอดี ไม่มีเศษทศนิยมคลาดเคลื่อน |
| 4 | ผู้ใช้ A เปิดใบเบิกของผู้ใช้ B โดยเดา URL | ผู้ทดสอบ A สร้างใบเบิก คัดลอก URL → ให้ผู้ทดสอบ B (คนละบัญชี บทบาทเดียวกัน) ลองเปิด URL เดียวกัน | ผู้ใช้ B ต้องเห็นหน้า "ไม่มีสิทธิ์เข้าถึง" (403) ไม่ใช่เนื้อหาใบเบิก |
| 5 | อัปโหลดไฟล์อันตรายปลอมเป็น PDF | เตรียมไฟล์ที่มีนามสกุล `.pdf` แต่เนื้อหาจริงเป็นสคริปต์ (ไม่ใช่ PDF จริง) → ลองแนบเป็นเอกสาร SDS ของสารเคมี | ระบบต้องปฏิเสธไฟล์ พร้อมข้อความแจ้งเตือน ไม่มีไฟล์ถูกบันทึกไว้ |
| 6 | พิมพ์เอกสาร F-01 (ใบเบิก) และ F-03 (บัญชีคุม) | พิมพ์ PDF ทั้งสองแบบ ตรวจสอบด้วยตา | ภาษาไทยแสดงผลถูกต้องทุกตัวอักษร (ไม่ใช่กล่องสี่เหลี่ยม/เครื่องหมายคำถาม), จัดวางอ่านง่าย, ข้อมูลครบถ้วนตรงกับหน้าจอ |

**หมายเหตุสำหรับผู้ประสานงาน UAT**: สถานการณ์ที่ 3, 4 (การทดสอบ concurrency 50 requests พร้อมกัน) และ 5
(ตรวจสอบ hash chain, DB grant) เป็นการทดสอบเชิงเทคนิคที่ครอบคลุมด้วยชุดทดสอบอัตโนมัติแล้ว (ดู
`tests/Feature/Ledger/ConcurrencyTest.php`, `tests/Feature/Security/DatabaseGrantRestrictionTest.php`) —
ไม่จำเป็นต้องให้ผู้ใช้จริงทำซ้ำ เว้นแต่ต้องการยืนยันด้วยตาตนเองอีกครั้งก่อน Go-Live

## ส่วนที่ 2: สถานการณ์ทดสอบตามกระบวนการทำงานจริง (End-to-End ต่อบทบาท)

### 2.1 นิสิต (STUDENT)

| # | สถานการณ์ | เกณฑ์ผ่าน |
|---|---|---|
| S1 | ล็อกอินครั้งแรกผ่าน MEDSCI ACC | เข้าสู่ระบบสำเร็จ, เห็นหน้ายืนยันความเป็นส่วนตัว, กรอกข้อมูลเพิ่มเติมได้ครบ |
| S2 | สร้างใบขอเบิก 1 รายการ ระบุอาจารย์ที่ปรึกษา | สร้างสำเร็จ สถานะเป็น "ร่าง" |
| S3 | เพิ่ม/ลบรายการในใบเบิกก่อนส่ง | เพิ่ม-ลบได้อิสระตราบใดที่ยังไม่ส่ง |
| S4 | ส่งใบเบิก | สถานะเปลี่ยนเป็น "ส่งแล้ว รอพิจารณา", อาจารย์ที่ปรึกษาได้รับอีเมลแจ้งเตือน |
| S5 | ไปรับของจริงที่ห้องปฏิบัติการ ยืนยันด้วยลายเซ็น/OTP | ได้รับของ, ใบเบิกอัปเดตสถานะถูกต้อง |
| S6 | คืนของที่เบิกเกิน | คืนสำเร็จ ยอดคงเหลือของขวดที่คืนเข้าถูกต้อง |
| S7 | พิมพ์ใบเบิกเป็น PDF, สแกน QR Code ตรวจสอบ | PDF ถูกต้อง, สแกน QR แล้วเปิดหน้ายืนยันเอกสารได้โดยไม่ต้องล็อกอิน |

## ส่วนที่ 3: สรุปผลและเกณฑ์ Go/No-Go

- ผ่านทั้งหมดในส่วนที่ 1 (ตาราง Acceptance Criteria) — **บังคับ ไม่มีข้อยกเว้น**
- ผ่านอย่างน้อย 90% ของสถานการณ์ในส่วนที่ 2 ต่อบทบาท — ข้อที่ไม่ผ่านต้องมีแผนแก้ไขและกำหนดเวลาที่ชัดเจน
  ก่อนอนุมัติ Go-Live
- ทุกข้อที่ทำเครื่องหมาย ❌ ต้องมีรายงานแนบ (ภาพหน้าจอ/ขั้นตอนที่ทำให้เกิดปัญหา) ส่งกลับทีมพัฒนา
